Anyone can run Terraform. Installing it everywhere you operate is the part that scales badly — your
workstation, every other developer's workstation, and every CI runner, on machines that are rarely the same
distribution. Pinning a different version per environment makes it harder still, because most package
managers install one version of a package system-wide and have no notion of concurrent versions. Atmos now
installs and pins those tools itself, reading the same `.tool-versions` file asdf already uses and pulling
package definitions from the Aqua registry.

<!--truncate-->

## The Problem

Terraform and OpenTofu have to be present everywhere infrastructure gets run. That is a workstation, someone
else's workstation running a different distribution, and a CI runner that starts from nothing every time. The
install step is different in each place, and keeping the three in agreement is manual work that nobody owns.

Pinning versions per environment is the second half. Holding dev on one version and production on another,
and moving each deliberately rather than whenever a package manager decides, is ordinary operational
practice. Most package managers cannot express it: they install one version system-wide, so running two
concurrently means working around the package manager rather than with it.

The usual answer is a dedicated tool manager, which comes with its own costs:

- Another binary every contributor and every CI job has to install first
- Another config file, separate from the stack configuration that actually describes the deployment
- Context switching between the tool that runs your infrastructure and the tool that installs the tools
- No connection between a component's declared requirements and what is actually on the PATH when it runs

## The Fix

Atmos installs and pins CLI tools directly. Versions live in a `.tool-versions` file in asdf format, so an
existing file works unchanged, and package definitions come from the
[Aqua registry](https://github.com/aquaproj/aqua-registry) — a community-maintained collection of over 1,000 CLI
tool definitions covering terraform, kubectl, helm, k9s, aws-cli, and hundreds more.

Tool names resolve in three steps, so short names work without memorizing registry paths:

1. **Exact matches**: `hashicorp/terraform` → `hashicorp/terraform`
2. **Alias resolution**: `terraform` → `hashicorp/terraform`
3. **Registry lookup**: searches the Aqua registry for canonical paths

That is how `k9s` finds `derailed/k9s` without you typing it.

## Migration from Other Tool Managers

### From asdf

Existing asdf `.tool-versions` files work as-is — no conversion step:

```bash
# Your existing .tool-versions file works as-is
terraform 1.9.8
kubectl 1.28.0
helm 3.13.0

# Just use Atmos toolchain commands instead
atmos toolchain install
atmos toolchain list
```

### From Aqua

Convert an `aqua.yaml` into a `.tool-versions` file:

```bash
# Convert aqua.yaml to .tool-versions
grep -E '^\s+name:' aqua.yaml | \
  sed 's/name://' | \
  xargs -I {} atmos toolchain add {}

# Then use Atmos toolchain
atmos toolchain install
```

### From tfenv, rbenv, or pyenv

Record what you are running today, then let Atmos install it everywhere else:

```bash
# Check current versions
terraform version
kubectl version --client

# Add to .tool-versions
echo "terraform $(terraform version | head -1 | awk '{print $2}' | tr -d 'v')" > .tool-versions
echo "kubectl $(kubectl version --client -o json | jq -r '.clientVersion.gitVersion' | tr -d 'v')" >> .tool-versions

# Install via Atmos
atmos toolchain install
```

Nothing else in your project changes. Toolchain commands are additive, and existing component and stack
configuration is untouched.

## How to Use It

### Getting started

When you run `atmos toolchain list` without a `.tool-versions` file, Atmos tells you what to do next:

```
# No Configuration Found

No .tool-versions file found at: .tool-versions

## To get started:

Add a tool to automatically create your configuration:

atmos toolchain add terraform@1.6.0

Then list your tools:

atmos toolchain list
```

### Installing tools

```bash
# Install specific versions using aliases
atmos toolchain install terraform@1.9.8
atmos toolchain install opentofu@1.10.3
atmos toolchain install kubectl@1.28.0
atmos toolchain install k9s@0.32.7

# Install using canonical registry paths
atmos toolchain install hashicorp/terraform@1.9.8
atmos toolchain install opentofu/opentofu@1.10.3
atmos toolchain install derailed/k9s@0.32.7

# Install all tools from .tool-versions file
atmos toolchain install
```

### Managing versions

Versions live in a `.tool-versions` file, in the same format asdf uses:

```
terraform 1.9.8
opentofu 1.10.3
kubectl 1.28.0
helm 3.13.0
k9s 0.32.7
```

```bash
# Add tools to .tool-versions
atmos toolchain add terraform@1.9.8
atmos toolchain add k9s@0.32.7

# Remove a tool from .tool-versions
atmos toolchain remove terraform

# Set default version when multiple are installed
atmos toolchain set terraform 1.9.8

# List installed tools with status
atmos toolchain list

# Remove unused tool versions
atmos toolchain clean
```

The `list` command prints a table of tool aliases and registry paths, installed versions and their status
(✓ or ✗), installation dates and binary sizes, and every version when more than one is configured.

### Running tools

```bash
# Execute a specific version
atmos toolchain exec terraform@1.9.8 -- plan

# Use the version from .tool-versions
atmos toolchain exec terraform -- plan

# Execute k9s for Kubernetes cluster management
atmos toolchain exec k9s -- version
atmos toolchain exec k9s@0.32.7 -- info

# Get tool paths for integration
atmos toolchain path
atmos toolchain which terraform
atmos toolchain which k9s
```

If you would rather not prefix every invocation, put the managed tools on your PATH:

```bash
export PATH="$(atmos toolchain path):$PATH"
terraform version
k9s version
```

### Finding tools

```bash
# List all available tools in the Aqua registry
atmos toolchain registry list aqua

# Search for specific tools
atmos toolchain registry search terraform
atmos toolchain registry search kubectl
atmos toolchain registry search k9s

# Get detailed information about a tool
atmos toolchain info terraform
atmos toolchain info k9s

# Get available versions for a tool
atmos toolchain get k9s
atmos toolchain get terraform --all --limit 10
```

## Declaring Tools Alongside Components

Tool requirements can live in stack configuration, at three levels, with the usual inheritance. This is where
per-environment pinning comes from: a stack already describes one environment, so a tool version declared in
it applies to that environment and nothing else. Dev can sit on one version and production on another, and
each moves when you change its stack rather than when a package manager decides.

```yaml
# Global dependencies (applies to every component in this stack)
dependencies:
  tools:
    aws-cli: "2.0.0"
    jq: "latest"
    k9s: "0.32.7"

# Component type dependencies (applies to all terraform components)
terraform:
  dependencies:
    tools:
      terraform: "1.9.8"
      tflint: "0.54.0"

# Component instance dependencies (specific component)
components:
  terraform:
    vpc:
      dependencies:
        tools:
          terraform: "1.9.8"
          checkov: "latest"
    eks-cluster:
      dependencies:
        tools:
          terraform: "1.9.8"
          kubectl: "1.28.0"
          k9s: "0.32.7"
```

When you provision a component, Atmos:

1. Resolves tool dependencies from stack configuration (with inheritance)
2. Installs missing tools
3. Updates PATH to include installed tools
4. Executes the component with the correct tool versions

Every component runs with exactly the tools it declares, which is what removes the version conflicts. The same
`dependencies.tools` block works for workflows and custom commands.

## Configuration

Point Atmos at a different versions file or install directory through environment variables:

```bash
export ATMOS_TOOL_VERSIONS=/path/to/.tool-versions
export ATMOS_TOOLS_DIR=/custom/tools/dir
export ATMOS_TOOLCHAIN_GET_ALL=true
export ATMOS_TOOLCHAIN_GET_LIMIT=50
```

Or per invocation, through flags:

```bash
atmos toolchain list --tool-versions /path/to/.tool-versions
atmos toolchain get terraform --all --limit 20
```

Or as defaults in `atmos.yaml`:

```yaml
toolchain:
  versions_file: .tool-versions
  install_path: .tools
```

Precedence: **flags > environment variables > config files > defaults**

Downloaded tools are cached under `$XDG_CACHE_HOME/atmos/toolchain` (or `~/.cache/atmos/toolchain`), following the
[XDG Base Directory Specification](https://specifications.freedesktop.org/basedir-spec/basedir-spec-latest.html).
If XDG directories are unavailable, the cache falls back to `~/.cache/tools-cache`. Set `XDG_CACHE_HOME` or
`ATMOS_XDG_CACHE_HOME` to move it. The whole thing works the same way on Linux, macOS, and Windows.
