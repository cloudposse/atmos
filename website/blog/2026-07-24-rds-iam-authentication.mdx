You want to connect to an RDS database with IAM authentication instead of a static password — the
right call for security. But it means installing the AWS CLI, running `aws rds generate-db-auth-token`,
remembering a fistful of arguments, and resolving AWS credentials separately from the identity system
you already use for every other AWS operation in Atmos. In CI, that is one more tool to install and
one more credential path to wire up, just to hand a password to `psql`.

<!--truncate-->

## The Problem

RDS and Aurora support IAM database authentication: instead of a long-lived password, a client
presents a short-lived, SigV4-signed token as the password over a TLS connection. It is a real
security win — no shared database passwords to rotate or leak.

The catch is getting that token in front of your client. The standard path is
`aws rds generate-db-auth-token`, which needs the AWS CLI installed and a set of AWS credentials
resolved on its own — outside the Atmos identity system that already manages your SSO, OIDC, and
assume-role chains. So you end up with two credential paths to keep in sync, an extra binary in every
CI image, and a handful of arguments to remember, all to produce a password.

## The Fix

Atmos can now open an interactive database session straight from an Atmos identity — no AWS CLI, no
static password, and in the common case, no connection arguments to remember. Declare the database
once as an `aws/rds` integration:

```yaml
auth:
  integrations:
    dev/rds/app-db:
      kind: aws/rds
      via:
        identity: dev-admin
      spec:
        database:
          host: mydb.abc123.us-east-2.rds.amazonaws.com
          port: 5432
          username: app
          region: us-east-2
```

…then connect by name:

```shell
atmos aws rds connect dev/rds/app-db
```

That is the whole command — no host, port, user, or region to retype each time (the same "don't make
me supply five arguments" ergonomics that make `gh auth token` so pleasant). Flags
(`--host`/`--port`/`--username`/`--region`) are still there for a one-off or to override the
integration, but day to day you just name the database.

`atmos aws rds connect` authenticates the identity, mints a fresh RDS IAM token locally (no AWS API
call), and opens `psql`/`mysql` for you. The token is passed to the client **only through the child
process environment** (`PGPASSWORD`/`MYSQL_PWD`) — never on the command line and never written to
disk. The connection is required to use TLS (`verify-full` for PostgreSQL, `VERIFY_IDENTITY` for
MySQL).

One real-world wrinkle it sidesteps: RDS server certificates chain to Amazon's own RDS CA, which is
usually absent from the OS trust store — a common cause of `verify-full`/`VERIFY_IDENTITY` failures
with other tools. Atmos embeds the
[Amazon RDS global certificate bundle](https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem)
and trusts it by default, so this just works. Pass `--ca-bundle` only to verify against a different one.

## Just Need the Token?

Sometimes you do not want Atmos to open the session — you want the raw token to hand to your own
client, a driver, or a CI step. `atmos aws rds token` mints just the token and writes it to `stdout`:

```shell
PGPASSWORD="$(atmos aws rds token \
  --host mydb.abc123.us-east-2.rds.amazonaws.com --port 5432 \
  --username app --region us-east-2 --identity dev-admin)" \
  psql "host=mydb.abc123.us-east-2.rds.amazonaws.com sslmode=require dbname=app user=app"
```

It is the RDS analog of `atmos aws eks token`: it authenticates the identity, builds the SigV4 token
locally, and writes it to `stdout` so it drops straight into `PGPASSWORD` or any driver's password
field. Because the token is the credential, it is written unmasked; the expiry is reported on `stderr`
so `stdout` stays a clean, pipeable value.

## How to Use It

1. Enable IAM database authentication on the instance or cluster and grant the database user IAM
   access (PostgreSQL `GRANT rds_iam`; MySQL/MariaDB `AWSAuthenticationPlugin`).
2. Give the identity an `rds-db:connect` IAM permission on the database user's resource ARN.
3. Run `atmos aws rds connect <integration>` (or `atmos aws rds token` for the raw token) — the
   connection uses TLS and IAM auth, with no password to manage.

See the [`atmos aws rds connect`](/cli/commands/aws/rds-connect) and
[`atmos aws rds token`](/cli/commands/aws/rds-token) command references and the
[RDS Authentication tutorial](/tutorials/rds-authentication) for the full flag list, integration
schema, and troubleshooting.
