Native Atmos labels and tags can now drive configuration as well as component selection. Mark a stack with
`pci: true`, use that label to include a PCI mixin, then use `--labels pci:true` to find the components that inherit it.
Native tags support the same pattern: a `pci` tag can enable configuration and select components with `--tags pci`.

## The Problem

Labels and tags already make components discoverable. But marking a stack as PCI-scoped did not automatically select
its configuration: you also had to maintain the right [mixin](/howto/mixins) imports. Classification and configuration
could drift apart.

## The Fix

Stack imports now accept a [`when` condition](/stacks/imports#conditional-imports) that can read native stack-wide
`metadata.labels` and `metadata.tags`. The same metadata can select the configuration a component inherits and identify
that component in list commands and other commands that support native selectors.

For example, the shared catalog defaults `audit_logging_enabled` to `false`. The PCI mixin enables it:

```yaml title="stacks/mixins/pci.yaml"
components:
  terraform:
    app:
      vars:
        audit_logging_enabled: true
```

Declare the classification in the stack, then use the label to select the mixin:

```yaml title="stacks/payments.yaml"
name: payments

metadata:
  labels:
    pci: true
  tags:
    - pci

import:
  - catalog/app
  - path: mixins/pci
    when: !cel labels.pci == true
```

The `app` component inherits both the metadata and the configuration selected by that label. A `standard` stack with
`pci: false` and no `pci` tag keeps the catalog default.

If you prefer a tag as the condition, replace the `when` line with:

```yaml
when: !cel "'pci' in tags"
```

Quote the entire CEL expression after the YAML tag. Tags are case-sensitive strings; labels can carry string or boolean
values. These are native Atmos selectors, separate from cloud resource tags.

## Configure, Find, and Inspect

<CastEmbed src="/casts/examples/conditional-imports/pci.cast" title="Configure and select components with metadata" chrome controls scrubber />

<TryExample example="conditional-imports">

```shell
# Find the component instances classified by the label.
atmos list instances --labels pci:true

# The tag selects the same payments/app instance in this example.
atmos list instances --tags pci

# Inspect the configuration selected by that metadata.
atmos describe component app -s payments --query .vars
# audit_logging_enabled: true

atmos describe component app -s standard --query .vars
# audit_logging_enabled: false
```

</TryExample>

`list instances` shows both the component and stack, so different instances of the same component remain distinguishable.
Other commands that support these selectors include `list components`, `list stacks`, `describe affected`, and bulk
Terraform operations. Use the selected component and stack with `describe component` to inspect its configuration.

The example requires no cloud credentials and creates no cloud resources. Its Terraform component displays the selected
configuration; it does not implement logging or establish PCI compliance.

## Keep the Classification Consistent

Import conditions use literal stack-wide metadata available when each import is reached. Earlier imports supply defaults;
the current manifest's labels override those defaults and flow into nested imports. Tags follow the configured list-merge
strategy, including structural `!append` lists. Later imports do not change decisions already made.

For the simplest connection between configuration and selection, declare the classification in the top-level stack and
let its components inherit it. Component-specific overrides or later imports can change the metadata selectors see after
the import decision. Computed metadata is unavailable to import conditions, even when it can be resolved for later selection.

Use an unquoted boolean for `labels.pci == true`. The string `"true"` does not satisfy that expression, although CLI label
selectors stringify both values. An absent tag does not match membership; for an optional label use
`has(labels.pci) && labels.pci == true`.

Checked-in metadata keeps local and CI configuration consistent. Conditions can also use CI detection (`ci`, `local`),
process environment variables (`env`), and combinations of conditions. An import whose condition does not match is not
read and contributes no configuration. See the [import reference](/stacks/imports#conditional-imports) for the full rules.
