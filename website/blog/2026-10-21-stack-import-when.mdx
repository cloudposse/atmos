Developers often authenticate interactively, while CI uses a workload identity. Both need to plan the same stack
against the same account and state, without changing resource configuration just because the command runs in a
pipeline. Stack imports can now select the authentication defaults for each environment with a `when` condition.

<!--truncate-->

## The Problem

Every entry in a stack manifest's [`import`](/stacks/imports) list was always processed. There was no way to say "pull
this file in only when running in CI" or "only when `DEPLOY_ENV` is `prod`". The `import:` list in `atmos.yaml` gained
exactly that with a `when` condition, which left stack manifests as the one place where imports could not be scoped.

## The Fix

An object-form stack import now accepts the same [`when` condition](/stacks/imports#conditional-imports) as the config
imports in `atmos.yaml`. When the condition does not match, Atmos never reads the file, so a skipped import cannot fail
and adds nothing to the stack.

A condition is one of these:

- `ci` imports the file only when Atmos detects a CI environment.
- `local` imports it only when Atmos does not.
- `always` and `never` import it unconditionally or not at all.
- `!cel <expression>` evaluates a [CEL expression](/steps#conditional-execution) that can read the process environment
  through `env`, for example `!cel env.DEPLOY_ENV == "prod"`.

A list of conditions requires all of them to hold. A condition that cannot be evaluated, such as an expression over an
environment variable that is not set, does not match, and the reason is written to the debug log.

## How to Use It

Assume your [shared authentication configuration](/tutorials/centralized-auth-config) already defines two identities:
`developer` for interactive access and `pipeline` for CI. Neither is marked as the default there. Both should target
the same cloud account and have the permissions needed to plan against the same backend.

Use small stack mixins to choose the default identity:

```yaml title="stacks/mixins/auth-local.yaml"
auth:
  identities:
    developer:
      default: true
```

```yaml title="stacks/mixins/auth-ci.yaml"
auth:
  identities:
    pipeline:
      default: true
```

Then import exactly one alongside the shared component configuration:

```yaml title="stacks/dev.yaml"
import:
  - catalog/app/defaults
  - path: mixins/auth-local
    when: local
  - path: mixins/auth-ci
    when: ci

vars:
  stage: dev
```

The same `atmos terraform plan app -s dev` command selects the developer identity locally and the pipeline identity
in CI. Skipped imports contribute no authentication defaults, so the inactive identity does not become a competing
default. Keep the backend, provider account and region, resource variables, and tags in the shared configuration.

:::note Keep local and CI plans comparable
Avoid using conditional imports to switch resource tags between checkout values and pipeline values. Those values
can differ even when the infrastructure code is identical, producing tag updates in a local plan after a CI apply.
Authentication is a better use case: change how you access the infrastructure while keeping its desired state the same.
:::

Both `ci` and `local` rely on the same CI detection as the rest of Atmos. Imports are processed while the stack
manifests are read, before Atmos knows which stack, component, or command it is running, so conditions can use CI
detection and the process environment, and nothing more specific.
