Trying an optional configuration should not require a second copy of a stack or repeatedly editing its imports.
Keep the configuration in a mixin and use a feature flag to decide whether to load it. Stack imports now support a
`when` condition, so the same stack can include an optional mixin only when its flag is enabled.

<!--truncate-->

## The Problem

A [mixin](/howto/mixins) groups configuration that a stack can reuse. Previously, every entry in a stack manifest's
[`import`](/stacks/imports) list was always processed. To try an optional mixin, you had to change the import list or
maintain a separate stack variant. There was no import-level condition to connect that choice to a feature flag.

## The Fix

An object-form stack import now accepts the same [`when` condition](/stacks/imports#conditional-imports) as the config
imports in `atmos.yaml`. When the condition does not match, Atmos never reads the file, so a skipped import cannot fail
and adds nothing to the stack.

A condition is one of these:

- `ci` imports the file only when Atmos detects a CI environment.
- `local` imports it only when Atmos does not.
- `always` and `never` import it unconditionally or not at all.
- `!cel <expression>` evaluates a [CEL expression](/steps#conditional-execution) that can read the process environment
  through `env`, for example `!cel env.FEATURE_MONITORING == "true"`.

A list of conditions requires all of them to hold. A condition that cannot be evaluated, such as an expression over an
environment variable that is not set, does not match, and the reason is written to the debug log.

## How to Use It

For an `app` component that accepts `detailed_monitoring_enabled`, keep monitoring off in the shared defaults:

```yaml title="stacks/catalog/app.yaml"
components:
  terraform:
    app:
      vars:
        detailed_monitoring_enabled: false
```

Put the optional setting in a mixin:

```yaml title="stacks/mixins/detailed-monitoring.yaml"
components:
  terraform:
    app:
      vars:
        detailed_monitoring_enabled: true
```

Import the defaults first, then gate the mixin on an environment variable:

```yaml title="stacks/dev.yaml"
name: dev

import:
  - catalog/app
  - path: mixins/detailed-monitoring
    when: !cel env.FEATURE_MONITORING == "true"
```

The flag is a process environment variable, not a stack variable. Only the string `true` enables this mixin; `false`
or an unset variable leaves the shared default in place. With an unset variable the expression cannot be evaluated,
so the import is skipped and the reason is available in debug logs.

Compare the resolved component configuration without provisioning anything:

```shell
FEATURE_MONITORING=false atmos describe component app -s dev --query .vars.detailed_monitoring_enabled
# false

FEATURE_MONITORING=true atmos describe component app -s dev --query .vars.detailed_monitoring_enabled
# true
```

The flag controls whether the mixin participates in the normal merge. When enabled, its value overrides the earlier
catalog default. You can group related settings in the same mixin as the feature grows.

:::note Keep flag values consistent
Changing a flag intentionally changes the desired configuration and can produce a Terraform diff. Use the same flag
values when comparing local and CI plans, and keep them consistent between planning and applying. Record the flags
alongside your deployment configuration so another workstation or pipeline can reproduce the same result. This flag
is independent of whether Atmos detects CI; running locally does not automatically turn it off.
:::

Both `ci` and `local` rely on the same CI detection as the rest of Atmos. Imports are processed while the stack
manifests are read, before Atmos knows which stack, component, or command it is running, so conditions can use CI
detection and the process environment, and nothing more specific.
