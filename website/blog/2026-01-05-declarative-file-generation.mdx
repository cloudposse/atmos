A Terraform component is rarely just Terraform. There is a `.tool-versions` pinning the binary, a `terragrunt.hcl` shim left over from a migration that is still half finished, a `locals.tf` whose contents differ per environment. Those files have to sit next to the component, and they have to agree with the stack configuration that drives it. Keeping them in agreement has meant a generator script or a habit of remembering. The `generate` section moves them into the stack manifest instead.

## The Problem

Atmos already generates the one auxiliary file everybody needs: the backend configuration. Every other file that belongs beside a component was somebody else's problem.

That covers more ground than it sounds like. Teams generate `.tool-versions` files so the right Terraform version is picked up in the component directory. Teams migrating off Terragrunt generate `terragrunt.hcl` shims so both tools can drive the same root module during the transition. Teams with per-environment constants generate a `locals.tf`. In each case the source of truth for the contents already lives in the stack manifest, and the file gets written by a wrapper script that has to be kept in step with it.

## The Fix

A `generate` section declares the files that should exist alongside a component. Map values are serialized according to the file extension; string values are rendered as Go templates with access to the component context.

```yaml
# Level 1: Global level (applies to all components)
generate:
  "global-context.json":
    level: "global"

terraform:
  # Level 2: Component type level (applies to all terraform components)
  generate:
    "terraform-context.json":
      level: "terraform-type"

  # Level 5: Overrides level (highest priority, file-scoped)
  overrides:
    generate:
      "override-context.json":
        level: "overrides"

components:
  terraform:
    vpc:
      vars:
        environment: prod
      # Level 4: Component level
      generate:
        # Map values are serialized based on file extension
        locals.tf:
          locals:
            environment: "{{ .vars.environment }}"

        # String values are treated as Go templates
        README.md: |
          # VPC Component
          Environment: {{ .vars.environment }}
```

- **Extension-aware serialization**: `.json`, `.yaml`, `.yml` files are serialized in their respective formats; `.tf` and `.hcl` files generate valid HCL
- **Go template support**: String values are processed as Go templates with full access to component context
- **5-level inheritance**: The `generate` section follows Atmos's standard inheritance model with merge from lowest to highest priority:
  1. **Global level** (`generate:` at stack root)
  2. **Component type level** (`terraform.generate:`)
  3. **Base component level** (via `metadata.inherits`)
  4. **Component level** (`components.terraform.vpc.generate`)
  5. **Overrides level** (`terraform.overrides.generate:`) - file-scoped, highest priority
- **CLI integration**: New `atmos terraform generate files` command with `--all`, `--dry-run`, and `--clean` flags
- **Auto-generation**: Enable `auto_generate_files: true` in `atmos.yaml` to automatically generate files during terraform commands
- **Clean integration**: Generated files are automatically cleaned up by `atmos terraform clean`

## How to Use It

### Single Component

```bash
atmos terraform generate files vpc -s prod-ue2
```

### All Components

```bash
atmos terraform generate files --all
```

### Preview Changes

```bash
atmos terraform generate files --all --dry-run
```

### Clean Generated Files

```bash
atmos terraform generate files --all --clean
```

### Automatic Generation

Add to `atmos.yaml`:

```yaml
components:
  terraform:
    auto_generate_files: true
```

The [generate files documentation](/cli/commands/terraform/generate/files) covers the remaining configuration options.
