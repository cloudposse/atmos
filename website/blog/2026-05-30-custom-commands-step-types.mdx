Every team eventually writes the deploy script that asks a few questions before it does anything dangerous. Which environment? Are you sure? The questions themselves are trivial, but answering them in a shell script means `read -p` loops, a dependency on `gum` or `fzf` for anything nicer, and a pile of ANSI escapes to make the output legible. Half the logic ends up in YAML and half in a script nobody wants to maintain. Atmos workflows and custom commands can now do the whole thing in one place.

<!--truncate-->

## The Problem

Interactive prompts have never been the hard part of a deployment script. Keeping them next to the deployment is.

A workflow that needs a confirmation has to shell out. That shell step needs a prompt library installed on every machine that runs it, or it degrades to a bare `read` that cannot show a list, filter options, or validate anything. Whatever the user typed then has to make it back into the workflow, which usually means an environment variable and a comment explaining the convention. Custom commands had the same gap. The usual escape hatch — a standalone wrapper script checked into the repository — keeps the prompts and the logic together, but it never appears in `atmos help`, so nobody outside the team that wrote it finds it.

## The Fix

Workflows and custom commands share one set of step types, so a prompt, a spinner, a table, and a `terraform apply` are all steps in the same list:

- **Interactive**: `input`, `confirm`, `choose`, `filter`, `file`, `write`
- **Status messages**: `toast`, `markdown`
- **Output**: `spin`, `table`, `pager`, `format`, `join`, `style`, `linebreak`, `log`
- **Terminal**: `alert`, `title`, `clear`, `env`, `exit`
- **Command**: `shell`, `atmos`

Status messages are one step type, not four. Use `type: toast` and pick the styling with `level: success`, `info`, `warn`, or `error`. For a message that belongs in the log stream rather than on screen, `type: log` takes the same `level` field and writes through the Atmos logger.

The `shell` and `atmos` types continue to work exactly as before — this is purely additive.

## How to Use It

### Workflow Example

```yaml title="stacks/workflows/deploy.yaml"
workflows:
  deploy:
    description: Interactive deployment workflow
    steps:
      - name: env
        type: choose
        prompt: "Select target environment"
        options: [dev, staging, prod]
        default: dev

      - name: confirm
        type: confirm
        prompt: "Deploy to {{ .steps.env.value }}?"

      - name: deploy
        type: atmos
        command: terraform apply vpc -s {{ .steps.env.value }}

      - type: toast
        level: success
        content: "Deployment to {{ .steps.env.value }} completed!"
```

Run with: `atmos workflow deploy -f deploy`

### Custom Command Example

```yaml title="atmos.yaml"
commands:
  - name: deploy-wizard
    description: Interactive deployment wizard
    steps:
      - name: env
        type: choose
        prompt: "Select target environment"
        options: [dev, staging, prod]
        default: dev

      - name: prod_warning
        type: toast
        level: warn
        content: "You are about to deploy to PRODUCTION!"

      - name: confirm
        type: confirm
        prompt: "Deploy to {{ .steps.env.value }}?"
        default: false

      - name: deploy
        type: atmos
        command: terraform apply vpc -s {{ .steps.env.value }}

      - name: done
        type: toast
        level: success
        content: "Deployment to {{ .steps.env.value }} completed!"
```

Run with: `atmos deploy-wizard`. Because it is a real command, it also shows up in `atmos help`.

### Multi-Select Components

```yaml
commands:
  - name: deploy-components
    description: Select and deploy multiple components
    steps:
      - name: components
        type: filter
        prompt: "Select components to deploy"
        multiple: true
        options: [vpc, eks, rds, s3, lambda]

      - name: summary
        type: markdown
        content: |
          ## Deployment Summary
          You selected **{{ len .steps.components.values }}** components:
          {{ range .steps.components.values }}
          - {{ . }}
          {{ end }}

      - name: confirm
        type: confirm
        prompt: "Proceed with deployment?"

      - type: shell
        command: |
          {{ range .steps.components.values }}
          echo "Deploying {{ . }}..."
          {{ end }}
```

### Input Collection

```yaml
commands:
  - name: create-ticket
    description: Create a deployment ticket
    steps:
      - name: title
        type: input
        prompt: "Ticket title"
        placeholder: "Brief description of the change"

      - name: description
        type: write
        prompt: "Detailed description"

      - name: priority
        type: choose
        prompt: "Priority level"
        options: [low, medium, high, critical]
        default: medium

      - type: toast
        level: success
        content: |
          Ticket created:
          Title: {{ .steps.title.value }}
          Priority: {{ .steps.priority.value }}
```

## Variable Passing

Access previous step results using Go templates:

- `{{ .steps.<name>.value }}` - Primary value (string)
- `{{ .steps.<name>.values }}` - Multiple values (for multi-select)
- `{{ .steps.<name>.metadata.<key> }}` - Metadata like `exit_code`, `stdout`, `stderr`
- `{{ .env.<VAR> }}` - Environment variables

For the complete step type reference, see the [custom commands documentation](/cli/configuration/commands/steps#extended-step-types) and the [workflows documentation](/workflows/steps/type).
