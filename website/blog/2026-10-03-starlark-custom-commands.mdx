Small automation tasks often need a separate interpreter, shell quoting, and commands
that turn structured configuration back into text. [Atmos Automation Language](/steps/type/script#embedded-starlark)
is a Python-like language for automating commands, workflows, and lifecycle hooks.
Built on Starlark and embedded in Atmos, it lets you run one executable file,
extend your project CLI, or check a component before an operation starts.

## The Problem

Even a short script has inputs to parse and failures to explain. Project commands
add flags and defaults; lifecycle checks also need the component's resolved
configuration. Repeating shell commands and parsing their output makes those small
pieces harder to reuse and test.

## The Fix

Use an Atmos shebang for a standalone program, or declare a `type: script` step
with `interpreter: starlark` inside a custom command or hook. All three use the same
embedded interpreter and built-in helpers. Hooks receive their component context
automatically. Larger programs can share functions and run independent tasks with
bounded concurrency.

## How to Use It

### Run an executable script

A [standalone script](/steps/type/script#standalone-script-spike) starts with
`#!/usr/bin/env atmos`. This example reads a JSON service manifest and totals its
replicas using the built-in `fs` and `json` helpers. Run
`./summarize.star services.json` with Atmos on your PATH; no additional interpreter
or JSON command-line tool is required.

### Add a project command

A [custom command](/cli/configuration/commands) gives the same kind of small program
a named CLI entry point. YAML defines the `capacity` command and its `--replicas`
flag. The Starlark step converts and validates the flag value, then calculates total
worker capacity. The flag travels through the step environment, keeping user input
out of the script source.

[View the full example](/examples/starlark-commands)

### Guard an operation with a hook

A [lifecycle hook](/stacks/hooks) attaches that logic to a component operation. This
example checks `ctx.component.vars` for an owner before Terraform plans. The `dev`
stack passes; the `unowned` stack inherits the component but clears its owner, so
the hook stops the plan. The tiny module has no providers or resources and needs
no cloud credentials.

### Grow into reusable functions

Keep the program in a file with the existing [include mechanism](/steps/type/script#loading-files):

```yaml
steps:
  - name: plan
    type: script
    interpreter: starlark
    script: !include scripts/plan.star
```

An included script [loads its helpers](/steps/type/script#loading-files) the way
you would expect: `load("components.star", ...)` inside `scripts/plan.star` resolves next to
that file, and the result is the same whether you run Atmos from the repository root or from
a component directory. Tracebacks name the file and line, such as `scripts/plan.star:7:8`.
Inline scripts written directly in YAML keep resolving against the step's working directory.

The larger release-plan demo runs `atmos release-plan api -s dev`. Its loaded function reads three
custom application components with at most two tasks running concurrently. The joined
results retain input order and include inherited versions and component-specific
replica counts. This command only reads configuration; it does not deploy anything.

<CastEmbed src="/casts/demo/fixtures/starlark/release-plan.cast" title="Starlark custom commands and parallel functions" chrome controls scrubber />

The recording's validator also runs in Starlark. It uses `fs.read_file`, `json.decode`,
and `regex` helpers to inspect cast events, check component output, and reject leaked
local paths. File reads are relative to the step working directory. Regular expressions
use Go/RE2 syntax; replacements are literal text.

Each output channel has one job. Use `print` for data, since it becomes the step's value when
no `output` is assigned. Use `ui.info` and its siblings for status messages, and the
[`log` builtin](/steps/type/script#logging) for diagnostics that appear only at the
configured log level. Script output [streams live](/steps/type/script#live-output) as
each line is produced, and lines from concurrent tasks carry the task name. Secret masking
applies to that streamed output too, even when a value arrives across separate writes.

Assertions read like ordinary Python. [Top-level `if` and `for`](/steps/type/script#language-features)
work in a script, so a [test step](/steps/type/test) can write
`if data["status"] != "ok": fail(...)` directly. When a suite fails, the error summarizes it as
"2 of 7 tests failed" and the report above it shows each failing case.

Starlark hooks can read inherited behavior controls through `ctx.component.settings`,
identify their event with `ctx.hook`, and inspect the parent result through
`ctx.operation`. Use `atmos.terraform("plan", component="vpc", stack="dev")` or
`atmos.helm(...)` for component operations. Other built-in commands are available
as functions too: `atmos.scaffold("generate", "template", "target")`, `atmos.vendor("pull")`,
`atmos.list("components")`, `atmos.describe("stacks")`, and `atmos.config("get", "base_path")`.
Use `atmos.run([...])` for any custom command. These calls share process capture, cancellation, and task retry behavior.
Before-hook results and uncaptured parent streams are explicitly `None`.

## Get Involved

Try a small command using the [Starlark reference](/steps/type/script) and
the `atmos-starlark` agent skill. Keep task retries around repeatable operations:
a retry repeats the whole function, while successful sibling tasks remain complete.
