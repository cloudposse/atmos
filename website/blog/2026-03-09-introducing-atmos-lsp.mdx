A stack file is just text until something reads it. Write `import:` as a mapping instead of a list, put a component under a key that should hold a map, or fat-finger the indentation, and the file still saves cleanly. You find out at `atmos terraform plan`, or worse, in CI ten minutes later. Every other language you work in tells you at the moment you type it.

Atmos now ships a Language Server Protocol server, so your editor reports those problems in the file where you made them.

<!--truncate-->

## The Problem

The edit-validate loop for infrastructure configuration runs through the terminal. You write YAML in an editor that treats it as generic YAML, save, switch windows, run `atmos validate stacks`, read a line number, switch back, and find the line. Nothing in that loop is hard — it is just slow enough that people skip it, which is how a malformed `components` section reaches a plan.

The same gap applies to `atmos.yaml` itself. Atmos publishes a JSON Schema for its own configuration, but unless your editor was told where to find it, a mistyped or removed setting looks exactly like a valid one.

## The Fix

Two pieces ship here, and they do different jobs.

**The Atmos LSP server** speaks LSP to your editor and answers three requests for Atmos files: diagnostics, completion, and hover.

Diagnostics fall into two groups depending on what kind of file you have open.

For stack files, Atmos parses the YAML and reports what it finds:

- Syntax errors from the YAML parser, positioned at the line and column the parser reports — `YAML syntax error: yaml: line 12: mapping values are not allowed in this context`.
- Structural problems in the sections Atmos owns: `'import' should be an array`, `'components' should be a map`, `'components.terraform' should be a map`, the same for `helmfile` and `kubernetes`, `'vars' should be a map`, and `Component name cannot be empty`.

Structural diagnostics are anchored at the top of the file rather than at the offending key, because the check runs against the parsed document rather than the token stream. The message names the path, so it is still actionable — but do not expect the squiggle to land on the line.

For `atmos.yaml` — including hidden variants, `atmos.d` fragments, and project-local profile fragments — Atmos validates the document against its generated configuration schema, the same one `atmos config schema` prints. Those diagnostics *are* positioned, because the validator maps each schema violation back to the YAML node that caused it. Deprecated configuration fields come back as warnings on the line that sets them.

Completion covers the Atmos vocabulary: the top-level keys (`import`, `components`, `vars`, `settings`, `metadata`), the component types (`terraform`, `helmfile`, `kubernetes`), the common stack variables (`namespace`, `tenant`, `environment`, `stage`, `region`, `enabled`, `tags`), and the settings blocks (`spacelift`, `atlantis`, `validation`). Hover returns short documentation with an example for each of those keys.

**The Atmos LSP client** is the other half. It launches and manages external language servers you already trust — `yaml-language-server`, `terraform-ls`, anything else that speaks LSP — routes each file to the servers that claim its extension, and merges the results into one diagnostic stream. That is what makes a single validation surface possible across a repository that holds both YAML stacks and HCL components.

## How to Use It

Start the server. Editors normally do this for you over stdio:

```bash
atmos lsp start
```

For remote development or for testing the server by hand, TCP and WebSocket transports are available:

```bash
atmos lsp start --transport=tcp --address=localhost:7777
```

Point your editor at it. Neovim, via `lspconfig`:

```lua
require('lspconfig').atmos.setup{
  cmd = { 'atmos', 'lsp', 'start' },
  filetypes = { 'yaml' },
  root_dir = function(fname)
    return require('lspconfig.util').root_pattern('atmos.yaml', '.git')(fname)
  end,
}
```

Any editor with a generic LSP client follows the same shape: run `atmos lsp start`, activate on YAML files, root the workspace at `atmos.yaml`. The [LSP Server guide](/lsp/lsp-server) has a per-editor feature matrix covering VS Code, Neovim, Vim, Emacs, Sublime Text, IntelliJ IDEA, Cursor, Zed, and Helix.

To bring external servers into the same stream, declare them in `atmos.yaml`:

```yaml
lsp:
  enabled: true
  servers:
    yaml-ls:
      command: "yaml-language-server"
      args: ["--stdio"]
      filetypes: ["yaml", "yml"]
      root_patterns: ["atmos.yaml", ".git"]
      initialization_options:
        yaml:
          validation: true
          hover: true
          completion: true

    terraform-ls:
      command: "terraform-ls"
      args: ["serve"]
      filetypes: ["tf", "tfvars", "hcl"]
      root_patterns: [".terraform", ".git"]
      initialization_options:
        experimentalFeatures:
          validateOnSave: true
```

Install those separately — `npm install -g yaml-language-server`, `brew install terraform-ls` — since Atmos launches them rather than bundling them.

The same machinery is available to AI assistants through the `validate_file_lsp` tool, which returns the aggregated diagnostics for a file with line and column numbers instead of the assistant guessing from the file contents. See the [tool documentation](/cli/configuration/ai/tools#available-tools).

## What Is Not There Yet

Worth stating plainly, because an LSP server invites assumptions:

- Go-to-definition is registered but returns nothing. Ctrl-clicking an import will not open the imported file yet.
- There is no spell-check or "did you mean" suggestion on component variables. Atmos does not know your Terraform module's variable names from the stack file, so a misspelled `vpc_cidr` is not flagged.
- Validation is per-file. Cross-file checks — does this import resolve, does this component exist — happen in `atmos validate stacks`, not in the editor.
- HCL files are routed to `terraform-ls`; the Atmos server itself does not validate them.

For editor-side setup beyond the examples above, see the [LSP client guide](/lsp/lsp-client).
