A mature AWS organization hands each engineer dozens of accounts, each with two or three permission sets. Every one of those has to be written down somewhere before a tool can assume it, and that somewhere is usually a hand-maintained list that goes stale the moment someone's access changes. AWS SSO already knows the whole list. Atmos can now read it directly: log in once, and every permission set you have access to is available as an identity.

<!--truncate-->

## The Problem

If you have access to 50 AWS accounts with multiple permission sets in each, the path to your first `atmos terraform plan` used to run through a few hundred lines of hand-written configuration:

- Clone the repository
- Read the documentation to understand identity configuration
- Query AWS SSO for the accounts and permission sets you can reach
- Write 50+ identity entries into `atmos.yaml` by hand
- Test authentication against each one

That list is tedious to produce, easy to get wrong, and out of date as soon as someone gains or loses a grant. For a new team member it stood between cloning the repository and running anything at all.

## The Fix

One line of provider configuration turns the hand-written list into a discovered one:

```yaml
# atmos.yaml
auth:
  providers:
    sso-prod:
      kind: aws/iam-identity-center
      start_url: https://my-org.awsapps.com/start
      region: us-east-1
      auto_provision_identities: true  # One line to enable
```

```bash
atmos auth login --provider sso-prod
# ✓ Provisioned 47 identities across 12 accounts (2.3s)

atmos terraform plan --identity sandbox/PowerUserAccess
# Works immediately - no additional configuration
```

At login, Atmos asks AWS SSO which accounts you can reach (`ListAccounts`) and which permission sets each of them grants you (`ListAccountRoles`), then writes the answer as an ordinary Atmos configuration file in the cache directory. Every later Atmos command imports that file *before* your own `atmos.yaml`, so anything you configure by hand takes precedence over anything that was discovered.

Provisioning never blocks you. If the discovery calls fail, Atmos logs a warning, authentication still succeeds, and you fall back to the identities you configured by hand — the same position you were in before the feature existed.

Re-authenticate and the list refreshes, so new accounts and permission sets show up without a configuration change. The same `atmos.yaml` works for everyone on the team, because each person discovers the identities their own SSO grants allow.

Discovered identities are named `{account-name}/{permission-set-name}`, which keeps names unique and makes the account and permission set obvious at a glance:

- `sandbox/PowerUserAccess`
- `staging/DeployerAccess`
- `dev/ReadOnly`

Auto-provisioning currently covers AWS IAM Identity Center. Support for other cloud platforms and identity providers is planned.

## How to Use It

### Enable it

Add `auto_provision_identities: true` to your AWS SSO provider:

```yaml
# atmos.yaml
auth:
  providers:
    sso-prod:
      kind: aws/iam-identity-center
      start_url: https://my-org.awsapps.com/start
      region: us-east-1
      auto_provision_identities: true  # Enable auto-provisioning
```

### See what you have

Run `atmos auth list` to see every identity, discovered or hand-written:

```bash
atmos auth list
# Authentication Configuration
# └──sso-prod (aws/iam-identity-center)
#    └──Identities
#       ├──● sandbox/PowerUserAccess (sso-prod) 11h58m
#       ├──● staging/DeployerAccess (sso-prod) 11h58m
#       ├──● production/DeployerAccess (sso-prod) 11h58m
#       └──● dev/ReadOnly (sso-prod) 11h58m
```

Discovered identities appear in the tree alongside the ones you wrote yourself. There is no visual distinction, because they are treated the same way.

### Override or extend a discovered identity

Naming a discovered identity in your `atmos.yaml` does not replace it. Atmos deep merges the two, so the fields you write are added to the fields that were discovered — and where both set the same field, yours wins:

```yaml
# atmos.yaml
auth:
  providers:
    sso-prod:
      kind: aws/iam-identity-center
      start_url: https://my-org.awsapps.com/start
      region: us-east-1
      auto_provision_identities: true

  identities:
    # Enhance provisioned identity with additional fields
    production/DeployerAccess:
      default: true        # Mark as default (merged with auto-provisioned fields)
      session:
        duration: 12h      # Extend from default 1h
```

Given this discovered identity:

```yaml
production/DeployerAccess:
  provider: sso-prod
  kind: aws/permission-set
  via:
    provider: sso-prod
  principal:
    name: DeployerAccess
    account:
      name: production
      id: "123456789012"
```

and that override:

```yaml
production/DeployerAccess:
  default: true
  session:
    duration: 12h
```

the identity Atmos uses is the union of both:

```yaml
production/DeployerAccess:
  provider: sso-prod           # ✅ From auto-provisioning
  kind: aws/permission-set     # ✅ From auto-provisioning
  default: true                # ✅ From manual config
  via:                         # ✅ From auto-provisioning
    provider: sso-prod
  principal:                   # ✅ From auto-provisioning
    name: DeployerAccess
    account:
      name: production
      id: "123456789012"
  session:                     # ✅ From manual config
    duration: 12h
```

That is how you mark a discovered identity as the default, stretch its session duration, or attach your own aliases, tags, and metadata without restating the provider and principal information Atmos already found.

### Find the files

Discovered identities are written under the [XDG Base Directory Specification](https://specifications.freedesktop.org/basedir-spec/basedir-spec-latest.html):

```
$XDG_CACHE_HOME/atmos/auth/
└── sso-prod/
    └── provisioned-identities.yaml
```

By default that resolves to `~/.cache/atmos/auth/` on Linux and macOS, and `%LOCALAPPDATA%\atmos\cache\` on Windows. The file is ordinary Atmos YAML, so you can read it, copy from it, or paste parts of it into your own configuration. On Linux and macOS:

```bash
cat ~/.cache/atmos/auth/sso-prod/provisioned-identities.yaml
```

Deleting the cache directory forces re-discovery, as does logging out and back in:

```bash
atmos auth logout --provider sso-prod
atmos auth login --provider sso-prod
```

## In Practice

For an organization with many AWS accounts, one login covers all of them:

```bash
# Before: Manually configure 50+ identities
# After: One login, 50+ identities available

atmos auth login --provider sso-prod
atmos terraform plan --identity sandbox/PowerUserAccess
atmos terraform plan --identity staging/DeployerAccess
atmos terraform plan --identity dev/ReadOnly
# All work without additional configuration
```

For a new team member, the first plan is three commands after the clone:

```bash
git clone https://github.com/acme/infrastructure
cd infrastructure
atmos auth login --provider sso-prod
atmos terraform plan --identity sandbox/PowerUserAccess
# Ready to deploy
```

The full set of configuration options lives in the [Authentication Documentation](/cli/commands/auth/usage).
