Different projects need different versions of Terraform, Helm, and other tools. Moving between them should not require reinstalling tools, changing a global default, or remembering which version to run. Declare what each project needs, and let the toolchain select it when you work in that project. Atmos [toolchain management](/cli/configuration/toolchain) brings that workflow to your infrastructure commands; this update makes it more consistent across projects, local development, and CI.

<!--truncate-->

## The Problem

Tools such as [asdf](https://asdf-vm.com/guide/introduction.html) and [mise](https://mise.jdx.dev/) make project-specific tool versions part of the development environment. You commit the versions a project needs, keep multiple versions installed on the same machine, and use the appropriate ones for the project at hand. Teammates can use the same declarations to set up their tools.

Infrastructure projects need that same experience. A Terraform upgrade in one repository should not force another repository to upgrade, and running a project's commands should not require manually managing executable paths.

Atmos already supports declared tool versions and automatic installation for execution dependencies. But paths tied to the invocation directory and installs that modified declarations made that workflow unpredictable. Using the environment could change the very configuration that defined it.

## The Fix

Your project declares its tools; Atmos resolves and installs them as needed when running its commands. This update keeps those declarations stable during automatic installation and resolves configured toolchain paths from the project base, so the same project settings apply when you work from a subdirectory.

Installed binaries continue to use shared XDG cache storage by default. Projects can select different versions while reusing installations of the same version. Atmos version switching follows the active project's toolchain settings too; outside a project, it keeps binaries and installation metadata in XDG storage.

For CI, opt-in frozen mode requires the artifacts to be recorded in advance and leaves the lockfile unchanged. Ordinary installs honor existing checksums and record missing version or platform entries after successful installation.

These changes use the existing files. The declaration file remains `.tool-versions`, and the artifact lockfile remains `toolchain.lock.yaml`. The `.tool-versions.lock` sidecar coordinates concurrent access; it is not another dependency declaration.

## How to Use It

Existing projects do not need a new toolchain configuration block to get these fixes. Atmos reads `.tool-versions` from the project base by default and stores binaries in shared XDG cache storage. Automatic installations leave your declarations unchanged. Tools are installed when a command needs them; changing directories alone does not trigger installation.

Lockfile use is enabled by default for current config editions. Its default location is `<install_path>/toolchain.lock.yaml`. To commit a lockfile with your project and use it in CI, override just its location:

```yaml title="atmos.yaml"
toolchain:
  lock_file: toolchain.lock.yaml
```

Generate it with [toolchain lock](/cli/commands/toolchain/lock), commit it, then enable frozen mode for CI installations:

```shell
atmos toolchain lock
ATMOS_TOOLCHAIN_FROZEN_LOCK_FILE=true atmos toolchain install
```

Frozen mode is opt-in. It requires a complete version and platform entry, including the artifact URL and checksum, even when the binary is already installed. It prohibits artifact lockfile writes and rejects lockfile refreshes. Prepare entries for every CI platform before enabling it.

### Compatibility and Config Editions

Projects pinned to a [config edition](/cli/configuration/edition) before `2026-08-05` retain `use_lock_file: false` as their default. Set `toolchain.use_lock_file: true` explicitly to enable ordinary lockfile use for those projects. Frozen mode requires lockfile verification regardless of that setting and defaults to disabled for every edition.

Relative `install_path`, `versions_file`, and `lock_file` paths, including the default `.tool-versions` path, now resolve against the configured project base. If you relied on paths relative to the invocation directory, set an absolute path or adjust your configuration. Automatic installs no longer add declarations; use intentional management commands to change them.

These path and installation behavior changes apply to every edition. Config editions currently preserve earlier default values, but cannot restore these earlier behaviors; an older edition pin does not provide that backward compatibility.
