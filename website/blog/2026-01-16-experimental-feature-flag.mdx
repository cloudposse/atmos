Every fast-moving tool has a line running through it, somewhere between the parts you can safely build a pipeline on and the parts that are still settling. That line is usually invisible. A command works, so someone uses it, and the team finds out it was provisional the day it changes. Atmos now draws the line where you can see it, and lets you decide what happens when someone crosses it.

<!--truncate-->

## The Problem

As Atmos evolves, we add capabilities like devcontainers, toolchain management, and Terraform backend provisioning. Those need real-world use before we can call them stable, which means they ship before their behavior is frozen. Until now nothing in the CLI told you which commands were in that state, and nothing stopped one from quietly becoming load-bearing in a CI pipeline.

## The Fix

Experimental features are now marked in the CLI, and the `settings.experimental` option lets you choose how Atmos handles them:

- **`warn`** (default) — Show a notification when running experimental commands, then continue
- **`silence`** — Run experimental commands without any notification
- **`disable`** — Block experimental commands entirely
- **`error`** — Show notification and exit with an error code

### CLI Visibility

Experimental commands are now clearly marked in help output with an `[EXPERIMENTAL]` badge:

```
AVAILABLE COMMANDS

      devcontainer [command] [EXPERIMENTAL]  Manage development containers
      terraform                              Execute terraform commands
      toolchain [command] [EXPERIMENTAL]     Manage CLI tool versions
```

When you run `--help` on an experimental command, you'll see a prominent badge at the top:

```
[EXPERIMENTAL]

Manage development containers with full lifecycle support.
```

## How to Use It

Control experimental features in `atmos.yaml`:

```yaml
settings:
  # Control experimental feature handling
  # Values: "silence", "disable", "warn" (default), "error"
  experimental: warn
```

Or via environment variable:

```bash
export ATMOS_EXPERIMENTAL=disable
```

### Per-Environment Settings

For local development, where trying a new command is the point:

```yaml
settings:
  experimental: warn  # See warnings but continue working
```

For CI and production, where nothing unstable should run at all:

```yaml
settings:
  experimental: disable  # Refuse to run experimental commands
```

Both `disable` and `error` refuse the command and exit non-zero. The difference is the output: `error` prints the experimental notice first, so the failing job's log names the feature that was blocked, while `disable` fails without it.

## Current Experimental Features

The following features are currently marked as experimental:

| Feature | Command | Description |
|---------|---------|-------------|
| Devcontainers | `atmos devcontainer` | Development container lifecycle management |
| Toolchain | `atmos toolchain` | Tool version management and installation |
| Backend Provisioning | `atmos terraform backend` | Terraform state backend management |
| Workdir Management | `atmos terraform workdir` | Component working directory management |
| Affected Components | `atmos list affected` | Identify changes for targeted CI/CD |
