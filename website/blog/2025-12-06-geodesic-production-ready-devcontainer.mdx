Every infrastructure repository has an unwritten prerequisite list. Terraform at some version, kubectl, helm, helmfile, three cloud CLIs, jq, yq, gomplate — and the specific combination that happens to work. New contributors spend their first day installing it, and everyone else's laptop drifts from everyone else's over the following months.

Containerizing that toolchain is the standard answer, and Geodesic is a container that already contains it.

<!--truncate-->

## The Problem

The tools are the environment. When they are installed per-laptop, "works on my machine" is not a joke about carelessness — it is the predictable result of ten independent installs with no shared source of truth. CI ends up on a different set again.

Containerized development environments — DevOps toolboxes — solved this before the [Development Containers specification](https://containers.dev/) existed. CoreOS pioneered the pattern: package the tools into an image, and a contributor needs only Docker and a shell. Geodesic has implemented it since 2016.

## The Fix

[Geodesic](https://github.com/cloudposse/geodesic) is Cloud Posse's DevOps toolbox — a container image with the infrastructure toolchain pre-installed and pre-configured. It predates the devcontainer spec, but it is the same concept, and Atmos treats it as what it is: a devcontainer.

What is in the image:

- **Atmos**
- **Terraform**, with all major providers
- **kubectl** and the Kubernetes tools — helm, helmfile, k9s, and more
- **Cloud CLIs** — AWS CLI, Azure CLI, Google Cloud SDK
- **Data processing** — jq, yq, gomplate
- **Development essentials** — git, make, vim, and more

It is Debian-based, built for linux/amd64 and linux/arm64, and usable as a base image for your own toolbox. Cloud Posse has shipped it since 2016.

With [Atmos's native devcontainer support](/changelog/native-devcontainer-support), you declare it in `atmos.yaml`:

```yaml
# atmos.yaml
devcontainer:
  geodesic:
    spec:
      name: "Geodesic DevOps Toolbox"
      image: "cloudposse/geodesic:latest"
      workspaceFolder: "/workspace"
      workspaceMount: "type=bind,source=${localWorkspaceFolder},target=/workspace"
      containerEnv:
        ATMOS_BASE_PATH: "/workspace"
      remoteUser: "root"
```

Then launch it:

```bash
atmos devcontainer shell geodesic
```

The only thing a contributor installs is Atmos. Terraform, the cloud CLIs, and the Kubernetes tools all arrive with the image. The host machine stays clean and the whole team runs identical versions.

## How to Use It

Zero to working environment:

```bash
# 1. Install Atmos (one binary)
brew install atmos

# 2. Navigate to your infrastructure repo
cd my-infrastructure

# 3. Launch Geodesic
atmos devcontainer shell geodesic

# You're in
$ atmos terraform plan vpc -s prod
$ kubectl get pods
$ helm list
```

The [`examples/devcontainer`](https://github.com/cloudposse/atmos/tree/main/examples/devcontainer) folder in the Atmos repository has a complete `atmos.yaml`, a `devcontainer.json`, and shell aliases — copy it as a starting point.

### Shell aliases for one-word access

Add an alias in `atmos.yaml`:

```yaml
# atmos.yaml
aliases:
  shell: "devcontainer shell geodesic"
```

Now the whole thing is:

```bash
atmos shell
```

This mirrors the classic Geodesic pattern where you'd type `./geodesic.sh` to launch your environment — same muscle memory, one less script in the repo.

### Identity injection

Geodesic works with Atmos's identity injection, so the container starts already authenticated:

```bash
# Launch Geodesic with AWS identity
atmos devcontainer shell geodesic --identity=aws-prod

# Launch with GitHub identity
atmos devcontainer shell geodesic --identity=github-main

# Works with any provider - Azure, GCP, custom providers
atmos devcontainer shell geodesic --identity=azure-prod
```

Inside the container, cloud provider SDKs pick up the authenticated identity. There is no credential file to configure by hand.

### Multiple instances

Each instance is an independent container with its own state:

```bash
# Separate environments
atmos devcontainer shell geodesic --instance=dev
atmos devcontainer shell geodesic --instance=prod

# Or per-person, on a shared machine
atmos devcontainer shell geodesic --instance=alice
atmos devcontainer shell geodesic --instance=bob
```

### Building on top of it

Use Geodesic as a base image when your organization has its own tools. Create a `Dockerfile`:

```dockerfile
# .devcontainer/Dockerfile
FROM cloudposse/geodesic:latest

# Add your organization's tools
RUN apt-get update && apt-get install -y \
    your-custom-tool \
    another-tool

# Add custom scripts
COPY scripts/ /usr/local/bin/

# Configure environment
ENV CUSTOM_VAR=value
```

Then point the spec at it instead of an image:

```yaml
# atmos.yaml
devcontainer:
  geodesic:
    spec:
      name: "Custom Geodesic Toolbox"
      build:
        dockerfile: ".devcontainer/Dockerfile"
        context: "."
        args:
          GEODESIC_VERSION: "latest"
      workspaceFolder: "/workspace"
      workspaceMount: "type=bind,source=${localWorkspaceFolder},target=/workspace"
      containerEnv:
        ATMOS_BASE_PATH: "/workspace"
      remoteUser: "root"
```

Atmos builds the image, tags it `atmos-devcontainer-geodesic`, and creates the container. Launching is unchanged:

```bash
atmos devcontainer shell geodesic

# Force rebuild after changing the Dockerfile
atmos devcontainer shell geodesic --replace
```

:::tip Example Available
The [`examples/devcontainer-build`](https://github.com/cloudposse/atmos/tree/main/examples/devcontainer-build) example has a working Dockerfile, devcontainer.json, and atmos.yaml for building custom Geodesic containers.
:::

### Pinning versions per project

Different projects can sit on different Geodesic versions without conflicting:

```yaml
# project-a/atmos.yaml
devcontainer:
  toolbox:
    spec:
      image: "cloudposse/geodesic:4.3.0"  # Pinned version
```

```yaml
# project-b/atmos.yaml
devcontainer:
  toolbox:
    spec:
      image: "cloudposse/geodesic:4.4.0"  # Different version
```

Each project gets the tool versions it was tested against.
