A custom command step used to be a string, which meant every property a step might need had to be smuggled into the shell. A timeout became `timeout 30s ...`. A working directory became `cd /app/infra && ...`. Retrying a flaky upload became a loop nobody wanted to read. The step syntax could express what to run and nothing about how to run it.

Steps can now be structured, carrying timeouts, working directories, retries, and an authentication identity as configuration instead of shell.

<!--truncate-->

## The Problem

Custom commands and workflows grew up separately in Atmos, and their steps diverged. Workflow steps had accumulated real structure; custom command steps were still a list of strings. The result was two vocabularies for the same idea, and a ceiling on what a custom command could express without reaching for shell tricks that are hard to read and harder to make portable across platforms.

## The Fix

The string form still works, unchanged:

```yaml
commands:
  - name: hello
    steps:
      - "echo Hello world!"
      - "echo Goodbye!"
```

A step can instead be a mapping, with its properties named:

```yaml
commands:
  - name: deploy
    steps:
      - name: validate
        command: terraform validate
        timeout: 30s
      - name: apply
        command: terraform apply -auto-approve
        timeout: 10m
        working_directory: /app/infra
```

Both forms coexist inside one command's step list, so an existing command can adopt structure only where it needs it:

```yaml
commands:
  - name: build
    steps:
      - "echo Starting build..."
      - name: compile
        command: make build
        timeout: 5m
      - "echo Build complete!"
```

## How to Use It

A structured step accepts `timeout` and `working_directory` as above, plus:

- `retry` — with `max_attempts`, `initial_delay`, and `max_delay` for backoff.
- `type` — `shell` by default, or `atmos` to run an Atmos command directly.
- `stack` — the stack an `atmos`-type step targets.
- `identity` — the authentication identity the step runs under.

Retrying a flaky upload, without a loop:

```yaml
commands:
  - name: sync
    steps:
      - name: upload
        command: aws s3 sync ./dist s3://mybucket
        retry:
          max_attempts: 3
          initial_delay: 1s
          max_delay: 30s
```

Running an Atmos command against a specific stack under a specific identity — the case that made multi-account deployment commands awkward before:

```yaml
commands:
  - name: deploy-all
    steps:
      - name: deploy-vpc
        command: terraform apply vpc
        type: atmos
        stack: prod-us-east-1
        identity: production-deployer
        timeout: 15m
```

Full reference: [Custom Commands documentation](/cli/configuration/commands).

## Where the Code Lives

The `Task` and `Tasks` types are in `pkg/schema/task.go`. The mixed syntax comes from `Tasks.UnmarshalYAML`, which inspects each sequence element: a scalar becomes a `Task` with `Command` set and `Type` defaulted to shell, and a mapping is decoded field by field. For configuration that arrives through Viper rather than `yaml.v3`, `TasksDecodeHook()` provides the equivalent mapstructure hook, registered in the decode chain in `pkg/config/load.go`.

Execution is not a separate path. `Task.ToWorkflowStep()` converts a task into a `schema.WorkflowStep`, and the custom command call site in `cmd/cmd_utils.go` hands that step to the shared step handler registry in `pkg/runner/step/`. Handlers there implement `StepHandler` (`Execute`, `Validate`, `RequiresTTY`), and they are the same handlers workflows use — which was the point of the change. `TaskFromWorkflowStep()` converts in the other direction.

Adding a step type means writing a handler and calling `Register()` from its `init()`, the pattern every file in `pkg/runner/step/` follows. The new type becomes available to custom commands and workflows at the same time.

## Get Involved

Existing custom command configurations are unaffected. If a step property you need is missing from the structured form, ask for it at https://github.com/cloudposse/atmos/issues
