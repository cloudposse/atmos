Define your resource tags once and let each environment supply its own stage,
region, and owner. With `!starlark`, stack manifests can use the
[Atmos Automation Language](/automation/language) to compute configuration
values from the component's effective configuration.

The same Starlark syntax that powers Atmos automation now works inside YAML
values. Write a function body, read `ctx.vars` or `ctx.metadata`, and return a
value. Atmos supplies the context after imports, inheritance, and overrides,
then passes the typed result to the component.

<!--truncate-->

## Put the rule next to the configuration

Add this to a shared component definition:

```yaml
vars:
  resource_tags: !starlark |
    return {
        "Environment": ctx.vars["stage"],
        "Region": ctx.vars["region"],
        "Owner": ctx.metadata.get("owner", "platform"),
    }
```

A development stack gets its development tags. A production stack gets its
production tags. Each expression reads the values of the component consuming
it, including that component's overrides.

Returned dictionaries and lists become native configuration values. A boolean
stays a boolean, a number stays a number, and strings keep their exact contents.

## Express the decision directly

Use conditions for environment-specific sizing, comprehensions for generated
lists, and local helper functions for repeated logic:

```yaml
vars:
  stage: prod
  minimum_replicas: !starlark |
    return 3 if ctx.vars["stage"] == "prod" else 1
  replicas: !starlark |
    return ctx.vars["minimum_replicas"] * 2
```

Atmos resolves computed dependencies when accessed, so these fields can appear
in either order. A circular dependency reports the fields involved.

## Inspect the result with Atmos

Run `atmos describe component <component> -s <stack>` to see the computed
configuration before deploying it. The evaluator ships in the Atmos binary,
with a read-only configuration context and a bounded interpreter step budget.

This host is focused on deriving configuration. Automation scripts provide
command execution, tool installation, prompts, and the step library; YAML
expressions provide typed values for the stack that uses them.

See the [`!starlark` reference](/functions/yaml/starlark) for context fields,
return types, template ordering, and examples.
