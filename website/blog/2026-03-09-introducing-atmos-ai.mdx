Asking a general-purpose coding assistant about your infrastructure means pasting. You paste a stack file, then the catalog it imports, then the mixin that catalog imports, then the output of `atmos describe component` so the model can see what the inheritance actually resolved to. By the time the assistant has enough context to be useful, you have done the work yourself.

Atmos AI closes that gap by running the introspection commands itself. It reads your stacks through the same code paths the CLI uses, so its answer reflects the configuration Atmos actually computes.

<!--truncate-->

## The Problem

Stack configuration is layered on purpose — imports, inheritance, overrides — and that layering is exactly what makes it hard to explain to something that can only see one file at a time. The questions people actually have ("what CIDR does production use", "which stacks include this component", "why is this variable set to that") are answered by the resolved configuration, not by any file on disk.

An assistant without access to the resolver either guesses or asks you to paste more. Both are worse than running the command.

## The Fix

Ask a question, and Atmos AI inspects your stacks, components, and configuration before it answers:

<Terminal title="atmos ai ask (Claude)">
```console
$ atmos ai ask "what stacks and components do we have in the infra?"

👽 Thinking...

  I'll list all the available stacks and components in your infrastructure.

  Based on the infrastructure configuration, here are the stacks and components:

  ## Stacks (4 total)

  1. **ue1-network** - Network stack in us-east-1
  2. **ue1-prod** - Production stack in us-east-1
  3. **uw2-network** - Network stack in us-west-2
  4. **uw2-prod** - Production stack in us-west-2

  ## Components by Stack

  ### ue1-network

  • tgw/attachment - Transit Gateway attachment
  • tgw/hub - Transit Gateway hub
  • vpc - Virtual Private Cloud

  ### ue1-prod

  • tgw/attachment - Transit Gateway attachment
  • vpc - Virtual Private Cloud

  ### uw2-network

  • tgw/attachment - Transit Gateway attachment
  • tgw/cross-region-hub-connector - Cross-region Transit Gateway connector
  • vpc - Virtual Private Cloud

  ### uw2-prod

  • tgw/attachment - Transit Gateway attachment
  • vpc - Virtual Private Cloud

  ## Summary

  Your infrastructure is organized across two AWS regions (us-east-1 and us-west-2),
  with dedicated network and production stacks in each region. The network stacks
  contain Transit Gateway hubs for network connectivity, while the production stacks
  use Transit Gateway attachments to connect to the network infrastructure. All stacks
  include VPC components for network isolation.
```
</Terminal>

Nothing in that answer was pasted in. The assistant called `atmos_list_stacks` and `atmos_describe_component`, the same introspection you would have run by hand.

## What It Can Reach

Tools are the whole story here, so it is worth being concrete about which ones exist.

Read-only introspection — `atmos_describe_component`, `atmos_list_stacks`, `atmos_validate_stacks` — plus file reads, web search, and `validate_file_lsp`, which returns editor-grade diagnostics with line and column numbers instead of the model inferring problems from the text. The [tool documentation](/cli/configuration/ai/tools) has the full list.

Two other sources of context matter as much as the tools:

**Project instructions.** An `ATMOS.md` file at the root of your repository is read into every session. It is plain Markdown, version-controlled alongside the stacks it describes, and it is where naming conventions, CIDR allocations, and "we always do it this way" belong. See the [project instructions documentation](/cli/configuration/ai/instructions).

**Skills.** Specialized skills carry tailored prompts and a narrower tool set for one domain each — `atmos-terraform`, `atmos-stacks`, `atmos-validation`, `atmos-components`, and the rest. Install the official set with one command, and switch between them mid-conversation with Ctrl+A:

```bash
atmos ai skill install cloudposse/atmos
```

Sessions persist in SQLite, so a conversation you name today is still there next week with its history intact — start an architecture discussion on Monday and resume it Friday with the earlier decisions still in context. See the [sessions documentation](/cli/configuration/ai/sessions).

## Picking a Provider

Seven providers are supported, and the right one depends on where your data is allowed to go:

| Provider | Best For | Privacy |
|----------|----------|---------|
| **Anthropic (Claude)** | Complex reasoning, analysis | Cloud |
| **OpenAI (GPT)** | Code generation, refactoring | Cloud |
| **Google (Gemini)** | Large context windows | Cloud |
| **xAI (Grok)** | Real-time knowledge | Cloud |
| **Ollama (Local)** | **Complete privacy, offline** | **100% Local** |
| **AWS Bedrock** | Enterprise, AWS-native | AWS |
| **Azure OpenAI** | Enterprise, Azure-native | Azure |

[Ollama](/cli/configuration/ai/providers#ollama-installation) runs models entirely on your machine — no API costs, no network egress, works offline. Regulated teams that still want a hosted model can use AWS Bedrock or Azure OpenAI for data residency and audit logging. You can switch providers mid-conversation with Ctrl+P.

Prompt caching cuts the cost of the repeated context — system prompts, project instructions — that every turn re-sends. Discounts vary by provider:

| Provider | Caching Discount |
|----------|-----------------|
| **Anthropic** | 90% |
| **OpenAI / Azure** | 50% |
| **Gemini** | Free |
| **Grok** | 75% |
| **Bedrock** | Up to 90% |

Most providers cache automatically. Anthropic needs explicit cache markers:

```yaml
ai:
  providers:
    anthropic:
      cache:
        enabled: true
        cache_system_prompt: true
        cache_project_instructions: true
```

## Permissions

An assistant that can run commands needs a boundary, and the boundary is declarative rather than per-prompt. Tools sort into three tiers:

- **Allowed** — run without asking. Read-only introspection like `atmos_describe_component`, `atmos_list_stacks`, and `read_file`.
- **Restricted** — require confirmation. Anything that writes: `edit_file`, `write_stack_file`, `write_component_file`.
- **Blocked** — never run. Arbitrary execution: `execute_bash_command`, `execute_atmos_command`.

Decisions you make at a confirmation prompt persist in `.atmos/ai.settings.local.json`, so you approve a given tool once per project rather than once per session. Every execution is logged with timestamp, user, and context.

## How to Use It

Configure a provider in `atmos.yaml`:

<File title="atmos.yaml">
```yaml
ai:
  enabled: true
  default_provider: "anthropic"
  providers:
    anthropic:
      model: "claude-sonnet-4-6"
      api_key: !env "ANTHROPIC_API_KEY"
```
</File>

Export the key (or `ollama pull llama4` if you are running locally), then start:

```bash
# Interactive chat, optionally named so you can resume it
atmos ai chat --session infrastructure-review

# One-shot question
atmos ai ask "What components are in production?"
```

For scripts and CI, `atmos ai exec` runs non-interactively and emits structured output:

```bash
result=$(atmos ai exec "Check for security issues" --format=json)
if echo "$result" | jq -e '.success == false'; then
  exit 1
fi
```

```json
{
  "success": true,
  "response": "Analysis complete...",
  "tool_calls": [{"tool": "atmos_list_stacks", "success": true}],
  "tokens": {"prompt": 120, "completion": 80, "cached": 50},
  "metadata": {"model": "claude-sonnet-4-6", "provider": "anthropic"}
}
```

Exit codes are standard, stdin piping works, and `--session` carries context across calls in a multi-turn script. See the [`atmos ai exec` documentation](/cli/commands/ai/exec).

To use the same tools from Claude Desktop, VS Code, Cursor, or any other MCP client, run Atmos as an MCP server:

```json
{
  "mcpServers": {
    "atmos": {
      "command": "atmos",
      "args": ["mcp", "start"]
    }
  }
}
```
