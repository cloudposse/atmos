Running `atmos terraform plan vpc -s dev` is not the same as running `terraform plan`. Atmos resolves the
component, generates the varfile and backend configuration for that stack, adds flags of its own, and then hands
the rest through to Terraform. Most of the time that is invisible and welcome — until you need to know whether
`-out` is yours to set, what `--skip-planfile` actually skips, or which of the flags in a command you copied off a
Terraform page will survive the trip. Every `atmos terraform` subcommand now has its own reference page that says
so explicitly.

<!--truncate-->

## The Problem

A wrapper around a well-documented tool inherits an awkward gap. The Terraform documentation describes flags that
Atmos may intercept, rewrite, or supply for you. The Atmos documentation described the orchestration model but not
the per-command surface. Anyone working out where one ended and the other began was reading source, running
`--help`, or guessing.

The gap shows up in ordinary places. Atmos writes a planfile by default with a name derived from the stack context,
which means `-out` behaves differently than you would expect from Terraform alone. Multi-component flags like
`--all`, `--affected`, and `--query` have no Terraform equivalent at all. And `--stack` is required for a reason
that only makes sense once you know Atmos generates the variables and backend config from it.

## The Fix

Each `atmos terraform` subcommand has a dedicated page covering what the command does with stack configuration
before Terraform ever runs, which flags Atmos owns, and which pass through untouched. Arguments and flags are
written as definition lists rather than tables, so a flag's description has room for the caveats, the config
equivalent in `atmos.yaml`, and a worked example. Pages also embed a recording of the command's `--help` output,
so you can see the real thing without leaving the page.

## How to Use It

Start from the command you are about to run.

### Core commands

- **[terraform plan](/cli/commands/terraform/plan)** - Generate execution plans with stack context
- **[terraform apply](/cli/commands/terraform/apply)** - Apply infrastructure changes
- **[terraform deploy](/cli/commands/terraform/deploy)** - Combined init, plan, and apply workflow
- **[terraform destroy](/cli/commands/terraform/destroy)** - Destroy infrastructure safely

### Generated files and metadata

- **[terraform generate backend](/cli/commands/terraform/generate/backend)** - Generate backend configurations
- **[terraform generate varfile](/cli/commands/terraform/generate/varfile)** - Generate variable files from stack configs
- **[terraform metadata](/cli/commands/terraform/metadata)** - Extract component metadata

### State management

- **[terraform state](/cli/commands/terraform/state)** - Advanced state manipulation
- **[terraform import](/cli/commands/terraform/import)** - Import existing resources
- **[terraform workspace](/cli/commands/terraform/workspace)** - Manage Terraform workspaces

### Development commands

- **[terraform fmt](/cli/commands/terraform/fmt)** - Format Terraform code
- **[terraform validate](/cli/commands/terraform/validate)** - Validate configuration syntax
- **[terraform test](/cli/commands/terraform/test)** - Run Terraform tests
- **[terraform console](/cli/commands/terraform/console)** - Interactive console for debugging

### Everything else
