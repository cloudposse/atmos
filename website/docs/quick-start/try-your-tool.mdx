[Install Atmos](/install), open a terminal in your existing repository, and run:

```shell
atmos stack add
```

Choose the deployment you already run. Atmos shows the component, stack, and manifest changes before you decide whether to save. For a CloudFormation template, start with `atmos aws cfn init`.

## CloudFormation

From the directory containing your templates, start the initializer.

```shell
atmos aws cfn init
```

Select your queue template. Enter `orders-blue, orders-green` for the AWS stack names and accept `dev` for the Atmos stack. Render the first instance locally.

```shell
atmos aws cfn render orders-blue -s dev
```

Both components belong to the Atmos stack `dev`. Each has its own AWS stack name. [Preview and deploy the instances](/cli/commands/aws/cloudformation/init).

## Terraform and OpenTofu

From your repository, point Atmos at the initialized root module you already plan. If your native plan uses extra varfiles, pass them in the same order to both the trial and registration. Here the root reads `vars/common.tfvars` first and `vars/dev.tfvars` second.

```shell
atmos terraform plan ./infra/network -- -var-file=vars/common.tfvars -var-file=vars/dev.tfvars
atmos stack add ./infra/network -s dev --var-file vars/common.tfvars --var-file vars/dev.tfvars
atmos terraform plan network -s dev
```

If your native plan uses only automatically loaded files such as `terraform.tfvars`, omit the varfile arguments. When both Terraform and OpenTofu are installed and the project does not identify the engine, select one at the prompt or supply `--command=terraform` or `--command=tofu`.

To use the same local root twice, give the second deployment its own state. For example, if production already uses the native workspace `blue` and `vars/prod.tfvars`, register it in the Atmos stack `prod`.

```shell
atmos stack add ./infra/network -s prod --workspace blue --var-file vars/common.tfvars --var-file vars/prod.tfvars
atmos terraform plan network -s prod
```

Here `network` is the component in both Atmos stacks. Its `dev` instance uses the workspace selected at first registration. Its `prod` instance uses the existing workspace `blue`. [Register and inspect deployments](/cli/commands/stack/usage#adopt-a-terraform-or-opentofu-root).

For a runnable example, use `atmos init examples/native-terraform`, enter `native-terraform`, and run `atmos terraform plan vpc -s dev`. The plan shows one local `null_resource` to add. [Explore the example](/components/terraform/brownfield).

## Terragrunt

From your live repository, point Atmos at a unit you already plan with Terragrunt 1.0 or later:

```shell
atmos terraform plan ./live/dev/vpc
atmos stack add ./live/dev/vpc -s dev
atmos terraform plan vpc -s dev
```

The first and third commands run Terragrunt in `live/dev/vpc`. Your plan shows the resources managed by that unit. The middle command saves `vpc` in the Atmos stack `dev`. If you also have `live/prod/vpc`, run `atmos stack add ./live/prod/vpc -s prod`, then `atmos terraform plan vpc -s prod`. [Preview the generated files](/cli/commands/stack/usage#adopt-a-terragrunt-unit).

## Atlantis

From a repository with a version 3 `atlantis.yaml`, list the projects first. For a project named `network-dev` with a built-in plan, save it and run its local plan.

```shell
atmos stack add ./atlantis.yaml --dry-run
atmos stack add ./atlantis.yaml --project network-dev -s dev
atmos terraform plan network-dev -s dev
```

The inventory identifies custom steps that need manual translation. Atlantis keeps its pull-request approvals and apply workflow. To try this with local state, run `atmos init examples/atlantis-import`, enter `atlantis-import`, and initialize the root with `terraform -chdir=infra/network init`. [Run the Atlantis import example](/examples/atlantis-import).

## Helm

If you already run `helm template web ./charts/web`, register that chart and render it by name. Pass any values files in the same order as your Helm command.

```shell
atmos stack add ./charts/web -s dev --release-name web --namespace preview -f values/dev.yaml
atmos helm template web -s dev
```

Here `dev` is the Atmos stack and `preview` is the Kubernetes namespace. To render a second release, repeat the first command with `--release-name web-canary`, then run `atmos helm template web-canary -s dev`. For a chart you can try locally, run `atmos init examples/helm`. [Helm example](/examples/helm)

## Packer

Register the directory you already pass to Packer. This example loads `images/alpine/inputs/dev.pkrvars.hcl`.

```shell
atmos stack add ./images/alpine -s dev --var-file inputs/dev.pkrvars.hcl
atmos packer init alpine -s dev
atmos packer validate alpine -s dev
```

When validation succeeds, run `atmos packer build alpine -s dev` to build the artifact. To register production, use `-s prod --var-file inputs/prod.pkrvars.hcl`. For a runnable local Docker build, use `atmos init examples/packer-docker`. [Packer example](/examples/packer-docker)

## Kubernetes and Kustomize

Render manifests without a cluster:

```shell
atmos init examples/kubernetes
cd kubernetes
atmos kubernetes render demo -s dev
```

The output includes the `atmos-demo` Namespace and a Deployment. For an overlay, copy [the Kustomize example](/examples/kustomize) and run the same render command in its directory.
