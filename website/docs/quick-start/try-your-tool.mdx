## CloudFormation

In your own project, register an existing template twice and render one instance locally:

```shell
atmos aws cfn init templates/queue.yaml --name orders-blue --name orders-green
atmos aws cfn render orders-blue -s dev
```

Both components belong to the Atmos stack `dev`. Each has its own AWS stack name. [Preview and deploy the instances](/cli/commands/aws/cloudformation/init).

## Terraform and OpenTofu

From a repository where you already run Terraform or OpenTofu, point Atmos at your initialized root module. For a root in `infra/network`, try the plan, then save it under the Atmos stack `dev`:

```shell
atmos terraform plan ./infra/network
atmos stack add ./infra/network -s dev
atmos terraform plan network -s dev
```

The first command runs your native plan in `infra/network`. If both CLIs are installed and the project does not identify an engine, choose one at the prompt or add `--command=tofu` or `--command=terraform`. The saved component remembers the choice. Registration supports local state and keeps the root’s selected workspace. [Register a second deployment](/cli/commands/stack/usage#adopt-a-terraform-or-opentofu-root).

For a runnable example, use `atmos init examples/native-terraform`, enter `native-terraform`, and run `atmos terraform plan vpc -s dev`. The plan shows one local `null_resource` to add. [Explore the example](/components/terraform/brownfield).

## Terragrunt

From your live repository, point Atmos at a unit you already plan with Terragrunt 1.0 or later:

```shell
atmos terraform plan ./live/dev/vpc
atmos stack add ./live/dev/vpc -s dev
atmos terraform plan vpc -s dev
```

The first and third commands run Terragrunt in `live/dev/vpc`. Your plan shows the resources managed by that unit. The middle command saves `vpc` in the Atmos stack `dev`. If you also have `live/prod/vpc`, run `atmos stack add ./live/prod/vpc -s prod`, then `atmos terraform plan vpc -s prod`. [Preview the generated files](/cli/commands/stack/usage#adopt-a-terragrunt-unit).

## Helm

If you already run `helm template web ./charts/web`, register that chart and render it by name. Pass any values files in the same order as your Helm command.

```shell
atmos stack add ./charts/web -s dev --release-name web --namespace preview -f values/dev.yaml
atmos helm template web -s dev
```

Here `dev` is the Atmos stack and `preview` is the Kubernetes namespace. To render a second release, repeat the first command with `--release-name web-canary`, then run `atmos helm template web-canary -s dev`. For a chart you can try locally, run `atmos init examples/helm`. [Helm example](/examples/helm)

## Packer

Register the directory you already pass to Packer. This example loads `images/alpine/inputs/dev.pkrvars.hcl`.

```shell
atmos stack add ./images/alpine -s dev --var-file inputs/dev.pkrvars.hcl
atmos packer init alpine -s dev
atmos packer validate alpine -s dev
```

When validation succeeds, run `atmos packer build alpine -s dev` to build the artifact. To register production, use `-s prod --var-file inputs/prod.pkrvars.hcl`. For a runnable local Docker build, use `atmos init examples/packer-docker`. [Packer example](/examples/packer-docker)

## Kubernetes and Kustomize

Render manifests without a cluster:

```shell
atmos init examples/kubernetes
cd kubernetes
atmos kubernetes render demo -s dev
```

The output includes the `atmos-demo` Namespace and a Deployment. For an overlay, copy [the Kustomize example](/examples/kustomize) and run the same render command in its directory.
