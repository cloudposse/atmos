<Intro>
Custom commands add project-specific subcommands to the Atmos CLI through YAML.
Use custom commands when you want your team to run a project task through a
familiar entry point such as `atmos capacity`. Define the interface in
`atmos.yaml` and compose the steps that implement it.
</Intro>

A **custom command** extends the `atmos` CLI. For example, your project can define
`atmos capacity` to calculate worker capacity, or a command that validates a
deployment. The command is available when Atmos loads your project's configuration.

## Define your subcommand

The following complete `atmos.yaml` adds a command named `capacity`. It is a
command this project defines, not a built-in Atmos command:

<EmbedFile filePath="examples/starlark-commands/atmos.yaml" />

The YAML defines the command name, description, `--replicas` flag, default, and
step to run. The embedded Atmos Automation Language program implements the
calculation and checks that the replica count is positive.

Atmos Automation Language is Python-like, built on Starlark, and embedded in
Atmos. Select it with `type: script` and `interpreter: starlark` on the step.
This example needs no stacks, components, or external tools.

## Run the command

Save the configuration as `atmos.yaml` and run from its directory:

```shell
atmos capacity --replicas 3
```

```text
✓ 3 replicas x 4 workers = 12 workers
```

Atmos discovers the custom command, parses its flag, and runs the script. Your
team uses the same command locally and in CI.

Omit the flag to use the default of two replicas:

```shell
atmos capacity
```

```text
✓ 2 replicas x 4 workers = 8 workers
```

Run `atmos capacity --help` to see the command description and generated flag help:

```text
--replicas string  Number of service replicas (default 2)
```

## Use inputs in your program

Script steps read parsed flags from `ctx.flags` and named positional arguments
from `ctx.arguments`. These mappings are read-only, and values stay data rather
than being inserted into the program's source.

The example declares `replicas` as a string flag, so the script converts
`ctx.flags["replicas"]` with `int()` before calculating. A boolean flag would
arrive as a boolean. The step calls `fail("replicas must be positive")` for zero
or negative counts, giving the caller a failed command with an actionable error.

Try `atmos capacity --replicas 0` to see that validation. No environment-variable
mapping or shell interpolation is required to pass the flag into the program.

## Grow the command

Custom commands can have multiple steps, named arguments, nested subcommands,
and component context. Start with the interface your team needs, then compose
the operations behind it. Move shared program logic into `.star` files when
several commands need the same behavior.

See the [custom command configuration reference](/cli/configuration/commands)
for the full YAML schema and the
[language reference](/automation/language) for language
helpers and execution controls. The
[complete runnable example](/examples/starlark-commands) contains the configuration
used throughout this guide.
