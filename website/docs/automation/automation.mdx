<Intro>
Add scripts to workflows, custom commands, and lifecycle hooks using the Atmos
Automation Language, based on Starlark.
</Intro>

Use your Atmos stacks, cloud identities, and toolchain to build, deploy, and test.
Combine built-in steps with shell commands; add scripts for conditions, loops,
and shared functions. Run the same commands locally and in CI.

## Choose an entry point {#choose-what-you-want-to-build}

| Build | Use it for |
| --- | --- |
| [A workflow](#workflows-and-parallel-tasks) | A sequence of tasks, with parallel execution, retries, and timeouts |
| [A custom command](#custom-commands) | An Atmos subcommand such as `atmos capacity` |
| [A lifecycle hook](#lifecycle-hooks) | Checks or actions before or after a component operation |
| [A test suite](#testing-your-automation) | Tests for scripts, command results, and deployed services |
| [A CLI app](#executable-scripts) | A standalone script with its own arguments, flags, and help |

## Workflows and parallel tasks

Define a workflow in YAML, then run it with
`atmos workflow <name> -f <file>`.

Combine Atmos commands, shell commands, scripts, and control steps for parallel
work, retries, and timeouts. The [workflow guide](/scripting/workflows) explains how to
define and run a workflow; the [step reference](/steps) describes the
building blocks.

Use script steps for conditions, loops, and data processing.
Store shared functions in `.star` files and include them from YAML; `load()`
resolves sibling modules relative to the script file.

Inside a program, `steps.task` describes a function call and `steps.parallel`
runs independent calls with a concurrency limit. Each task can have its own
timeout and retry policy. Results retain input order, and terminal output identifies
the task that produced it.

The [release-plan example](/steps/type/script#custom-components)
loads a shared function and reads three components with at most two tasks running
at once.

Use retries for operations that are safe to repeat: a retry runs the entire task
function again. See [task execution](/steps/type/script#embedded-starlark)
for the available controls and component-resolution deadline behavior.

Steps can collect user input and pass results to later steps. See
[prompts and step outputs](/scripting/workflows#collect-input-and-pass-results-between-steps).

arguments, flags, defaults, help, and steps. Commands can run existing tools or
Starlark scripts; Atmos parses inputs and passes them to the script.

## Lifecycle hooks

Run commands or scripts before or after component operations. A before-hook can
reject invalid configuration; an after-hook can check the result or run follow-up
tasks.

Starlark hooks receive `ctx.component`, `ctx.hook`, and `ctx.operation`, including
the component's resolved variables.

## Testing your automation

Use `test` steps to check script logic, command results, configuration, and
deployed services. In scripts, call `fail()` with a useful message when a check fails.

Group checks with the `test` step type to get a test tree and a summary of passed,
failed, skipped, and canceled checks. Successful output stays hidden by default;
failing checks show their captured output and error. Combine script checks with
HTTP checks, shell commands, and other supported step types. Use parallel or
matrix groups when checks can run independently.

Test groups work in workflows, custom commands, and lifecycle hooks.

## Custom CLI apps {#executable-scripts}

Run `.star` files directly with Atmos. No command registration in `atmos.yaml`
is required.

With Atmos on your `PATH`, save this as `hello.star`. The first line selects
Atmos as its interpreter. This example needs no stacks or external tools.

<File title="hello.star">
```python
#!/usr/bin/env atmos
name = ctx.args[0] if ctx.args else "world"
ui.success("Hello, {}!".format(name))
```
</File>

<Terminal title="Run the script">
```shell
chmod +x hello.star
./hello.star platform
```
</Terminal>

It prints `Hello, platform!`. You can also use `atmos hello.star platform`,
including on systems without shebang support.

### Declare script arguments and flags

Declare arguments, flags, and help with `cli.command`, `cli.arg`, and `cli.flag`.
Atmos parses and validates inputs before calling `main(args, flags)`.

```python
#!/usr/bin/env atmos
def validate(args, flags):
    if flags["replicas"] < 1:
        fail("replicas must be positive")

def main(args, flags):
    print("{}: {} replicas".format(args["service"], flags["replicas"]))

cli.command(
    description = "Report a service's replica count",
    args = [cli.arg("service", description="Service name")],
    flags = [cli.flag("replicas", type="int", shorthand="r", default=2)],
    validate = validate,
    run = main,
)
```

Save this as `replicas.star`. Run `atmos ./replicas.star api -r 3` (or `--replicas 3`),
or `atmos ./replicas.star --help` for generated usage. Help does not run `main`.
Flags support types, defaults, required values,
and choices; an optional `validate` callback handles checks involving multiple
inputs. Both callbacks receive parsed dictionaries directly.

See the [command declaration reference](/steps/type/script#declaring-a-standalone-command)
and [complete example](/examples/starlark-script).

## Language overview {#atmos-automation-language}

Atmos includes a Starlark interpreter with Python-like functions, conditions,
loops, and structured data.

Write `.star` files for standalone tools and shared code, or select
`interpreter: starlark` in a YAML script step. Use `load()` to share functions
between tools, custom commands, workflows, and hooks.

### Why Starlark?

Read [why Atmos uses Starlark](/scripting/language#why-starlark).

## Use the same automation locally and in CI

Commit your automation to the repository and run the same command locally and
in CI. Atmos supplies the interpreter; external commands still need their tools
and credentials.

Keep triggers and approvals in your CI system. Add [native CI](/ci) for Terraform
plan reporting, status checks, and planfile storage.

## Built-in helpers and reference

Atmos adds helpers for files, JSON, regular expressions, processes,
component lookup, command invocation, task execution, and terminal output.
`print` emits data; `ui` reports status; `log` emits diagnostics at the configured
log level. Output streams while scripts run. When masking is enabled, registered secrets
and matches for configured masking patterns are masked in displayed output.
