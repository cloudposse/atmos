<Intro>
Atmos CLI handles the execution layer — how you architect your cloud infrastructure, run automation
reproducibly across local and CI, and manage authentication. Atmos Pro is the control plane above
that, giving you visibility and coordination across all your teams, repositories, and environments.
</Intro>

<a href="https://atmos-pro.com"><img src="https://atmos-pro.com/api/media-kit/logo/badge/560x112/metallic" alt="Atmos Pro" width="280" height="56" /></a>

Atmos Pro is a [GitHub App](https://github.com/apps/atmos-pro). You install it on the GitHub
organization that owns your infrastructure repositories, and it turns GitHub Actions into an ordered,
drift-aware deployment engine for the Terraform and OpenTofu you already have.

## Why Atmos Pro?

**Atmos CLI** solves the problems every company encounters: structuring Terraform at scale, running
the same automation locally and in CI, handling auth, installing toolchains, managing component
dependencies, keeping configuration DRY with inheritance and templating, and vendoring components
across repositories. It owns the execution layer — plan, apply, deploy.

**Atmos Pro** solves what happens when you scale that up. Multiple repositories, multiple GitHub
organizations, dozens of teams, hundreds of components. You need to know what changed, what's
drifting, what's failing, who approved what, and what the current state of every deployment is —
across everything.

Your workflows run on your own GitHub Actions runners and authenticate to your cloud with your own
OIDC roles. Atmos Pro receives only what the CLI uploads — affected stacks, component inventories,
plan results — and coordinates on top of it:

- **Ordered deployments** — Dispatch plan and apply workflows in dependency order, on every PR and merge
- **Visibility** — See what's affected on every PR, across every repo and organization
- **Drift detection** — Know which stacks have drifted and trigger remediation automatically
- **Approvals** — Require independent human approval before changes are applied, with full audit trails
- **Failing runs** — Stay on top of failures across all teams without digging through CI logs
- **Stack locking** — Prevent concurrent modifications during deployments
- **Inventory** — Understand what's deployed, where, and with what configuration

## Get Started

Atmos Pro connects to your repositories through its GitHub App, so setup starts on
[atmos-pro.com](https://atmos-pro.com), not in your code. Once the app is installed and your
repositories are imported, you configure Atmos and your workflows to talk to it.

:::tip Working example
The [Atmos Pro Example Advanced](https://github.com/cloudposse-examples/atmos-pro-example-advanced)
repository is a fully working reference for every step below.
:::

### 1. Sign Up and Create a Workspace

Go to [atmos-pro.com](https://atmos-pro.com) and choose **Continue with GitHub**. Then create a
workspace for your company or team, or join one you've been invited to. A workspace groups your
repositories, team members, and settings.

### 2. Install the Atmos Pro GitHub App

From your new workspace, choose **Install** to add the
[Atmos Pro GitHub App](https://github.com/apps/atmos-pro) to your GitHub organization, and select
the repositories it may access.

- **GitHub organization administrators** choose **Install and Authorize**.
- **Everyone else** chooses **Authorize and Request**, which asks an administrator to approve the app.

The app is what lets Atmos Pro receive pull request webhooks, dispatch your workflows, and post
status checks and comments. Uploads from the CLI are rejected for repositories where it is not installed.

### 3. Import Repositories and Set Permissions

Import the repositories you want Atmos Pro to manage. Then configure
[repository permissions](https://atmos-pro.com/docs/learn/permissions) to control which branches,
environments, and workflow files may upload affected stacks, take locks, and report deployments.

### 4. Configure Your Workspace ID

Copy your workspace ID from the Atmos Pro workspace settings and store it as a GitHub Actions
variable. The workspace ID is not a secret.

<Terminal title="shell">
```bash
gh variable set ATMOS_PRO_WORKSPACE_ID --body "your-workspace-id"
```
</Terminal>

You can also commit it to `atmos.yaml`:

<File title="atmos.yaml">
```yaml
settings:
  pro:
    workspace_id: "your-workspace-id"
```
</File>

### 5. Enable Atmos Pro in Your Stacks

Tell Atmos Pro which workflows to dispatch for each GitHub event. A mixin keeps this in one place
for every stack:

<File title="stacks/mixins/atmos-pro.yaml">
```yaml
plan-wf-config: &plan-wf-config
  atmos-terraform-plan.yaml:
    inputs:
      component: "{{ .atmos_component }}"
      stack: "{{ .atmos_stack }}"

apply-wf-config: &apply-wf-config
  atmos-terraform-apply.yaml:
    inputs:
      component: "{{ .atmos_component }}"
      stack: "{{ .atmos_stack }}"
      github_environment: "{{ .vars.stage }}"

settings:
  pro:
    enabled: true
    pull_request:
      opened:
        workflows: *plan-wf-config
      synchronize:
        workflows: *plan-wf-config
    release:
      released:
        workflows: *apply-wf-config
```
</File>

See [Configure Atmos Stacks](https://atmos-pro.com/docs/configure/stacks) for merge queues, labels,
drift detection, and component dependencies.

### 6. Add the GitHub Actions Workflows

Atmos Pro needs four workflows in each repository:

<dl>
  <dt>Affected Stacks</dt>
  <dd>Runs `atmos describe affected --upload` on pull requests and merges so Atmos Pro knows what changed.</dd>

  <dt>Upload Instances</dt>
  <dd>Runs `atmos list instances --upload` on merges to the default branch and on a daily schedule to keep the inventory current.</dd>

  <dt>Plan</dt>
  <dd>Dispatched by Atmos Pro to run `atmos terraform plan` for each affected component.</dd>

  <dt>Apply</dt>
  <dd>Dispatched by Atmos Pro to run `atmos terraform deploy` for each approved component.</dd>
</dl>

Each workflow needs the `id-token: write` permission so Atmos can exchange a GitHub OIDC token
for a short-lived Atmos Pro token:

<File title=".github/workflows/atmos-pro-affected-stacks.yaml">
```yaml
name: Atmos Pro Affected Stacks

on:
  pull_request:
    types: [opened, synchronize, reopened, closed]

permissions:
  id-token: write   # Required for OIDC token exchange with Atmos Pro
  contents: read

jobs:
  affected:
    runs-on: ubuntu-latest
    env:
      ATMOS_PRO_WORKSPACE_ID: ${{ vars.ATMOS_PRO_WORKSPACE_ID }}
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 0
      - name: Upload affected stacks
        run: atmos describe affected --upload
```
</File>

## Authentication

Atmos Pro uses **GitHub OIDC token exchange** for authentication. No API keys or static credentials
are needed. When running in GitHub Actions with `id-token: write` permission, Atmos automatically
requests an OIDC token and exchanges it for a short-lived Atmos Pro bearer token.

Atmos Pro accepts the token only when three things line up: the repository has the Atmos Pro
GitHub App installed, the repository is imported into the workspace named by `workspace_id`, and
the workflow matches one of the workspace's repository permissions.

Cloud credentials are a separate OIDC flow between your workflows and your cloud provider. Atmos Pro
never holds them. See [Cloud Authentication](https://atmos-pro.com/docs/configure/cloud-authentication)
and [Auth](/stacks/auth).

## Features

### Affected Stacks

Upload the results of `atmos describe affected` to Atmos Pro for visibility into what changed
on each pull request. Atmos Pro correlates uploads with GitHub webhooks to dispatch plans in
dependency order and summarize the results on the pull request.

<Terminal title="shell">
```bash
atmos describe affected --upload
```
</Terminal>

### Component Instances

Upload a complete inventory of all component instances across all stacks. Atmos Pro uses this
to track what is deployed, where, and with what settings — across every repository in your
organization.

<Terminal title="shell">
```bash
atmos list instances --upload
```
</Terminal>

### Deployment Approvals

Combine Atmos Pro with [GitHub Environments](https://atmos-pro.com/docs/configure/github-environments)
to require verified Atmos Pro dispatches and independent human approval before changes are applied.

<AtmosProScreenshot
  view="approvals"

  caption="Reviewers see every pending approval across repositories, grouped by pull request."
/>

### Stack Locking

Prevent concurrent modifications to the same stack. Lock before apply, unlock after — Atmos Pro
tracks who holds the lock and when it was acquired.

<Terminal title="shell">
```bash
atmos pro lock vpc -s prod-use1
atmos terraform apply vpc -s prod-use1
atmos pro unlock vpc -s prod-use1
```
</Terminal>

### Drift Detection

Track Terraform plan results to detect infrastructure drift. When `--upload-status` is enabled,
Atmos uploads the plan exit code so Atmos Pro can identify stacks that have drifted from their
desired state and trigger remediation workflows.

<Terminal title="shell">
```bash
atmos terraform plan vpc -s prod-use1 --upload-status
```
</Terminal>

See [Configure Drift Detection](https://atmos-pro.com/docs/configure/drift-detection) to schedule
detection and remediation.

## Environment Variables

<dl>
  <dt>`ATMOS_PRO_WORKSPACE_ID`</dt>
  <dd>Workspace identifier for OIDC authentication. Not a secret. Maps to `settings.pro.workspace_id`.</dd>

  <dt>`ATMOS_PRO_BASE_URL`</dt>
  <dd>Override the Atmos Pro API base URL. Maps to `settings.pro.base_url`.</dd>

  <dt>`ATMOS_PRO_ENDPOINT`</dt>
  <dd>Override the API endpoint path. Maps to `settings.pro.endpoint`.</dd>

  <dt>`ATMOS_PRO_TOKEN`</dt>
  <dd>Internal runtime token from OIDC exchange (advanced/internal). Do not set this manually; configure `settings.pro.workspace_id` and GitHub Actions `id-token: write` instead.</dd>
</dl>

## Troubleshooting

### OIDC Authentication Failures

If `--upload` fails with an authentication error:

1. Check that the [Atmos Pro GitHub App](https://github.com/apps/atmos-pro) is installed on your repository
2. Verify your workflow has `id-token: write` permission
3. Confirm `ATMOS_PRO_WORKSPACE_ID` is set to the correct workspace

### Upload Access Denied (403)

If the upload succeeds authentication but returns a 403:

1. Verify the repository has been imported into your Atmos Pro workspace
2. Check that a repository permission in your workspace matches the workflow's branch, environment, and workflow file

See [Atmos Pro Troubleshooting](https://atmos-pro.com/docs/learn/troubleshooting) for more.
