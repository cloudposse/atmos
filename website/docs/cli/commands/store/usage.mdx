<Intro>
The `atmos store` command group manages raw values in the store backends configured under `stores:` in `atmos.yaml` (AWS SSM, AWS Secrets Manager, HashiCorp Vault, Azure Key Vault, GCP Secret Manager, Redis, Artifactory, 1Password, Keychain, GitHub Actions). Unlike [`atmos secret`](/cli/commands/secret/usage), store values need no declaration in stack configuration — any key can be read, written, or deleted directly by name against a named store. Values written here are readable via the [`!store`](/functions/yaml/store) and [`!store.get`](/functions/yaml/store.get) YAML functions, and by a [`type: store`](/workflows/steps/type/store) workflow step.
</Intro>

## Usage

```shell
atmos store <subcommand> [flags]
```

## Subcommands

<dl>
  <dt>[`set`](/cli/commands/store/set)</dt>
  <dd>Write a value to a store (create or update).</dd>

  <dt>[`get`](/cli/commands/store/get)</dt>
  <dd>Retrieve a value from a store.</dd>

  <dt>[`delete`](/cli/commands/store/delete) <em>(aliases `rm`, `unset`)</em></dt>
  <dd>Remove a value from a store.</dd>

  <dt>[`list`](/cli/commands/store/list)</dt>
  <dd>List configured store backends.</dd>
</dl>

## How It Works

1. **Configure a store backend** in `atmos.yaml`:

   ```yaml
   stores:
     app-metadata:
       kind: aws/ssm
       options:
         region: us-east-1
         prefix: /atmos/app-metadata
   ```

2. **Write and read values** with the CLI, scoped to a stack and component (or left global by omitting them):

   ```shell
   atmos store set app-metadata image_tag sha256:abc123 --stack=prod --component=ecs-service
   atmos store get app-metadata image_tag --stack=prod --component=ecs-service
   ```

3. **Read a value back in stack configuration** with the [`!store`](/functions/yaml/store) YAML function, without going through the CLI at all:

   ```yaml
   components:
     terraform:
       ecs-service:
         vars:
           image_tag: !store app-metadata prod ecs-service image_tag
   ```

## Store CRUD vs. declared secrets

`atmos store` and [`atmos secret`](/cli/commands/secret/usage) both read and write values in store
backends, but they solve different problems:

- **`atmos store`** operates on **any** configured store, with no declaration required. It is a
  direct CRUD interface to the backend: useful for pipeline metadata (an image tag, a build
  number, a deployment marker) that doesn't belong in stack configuration as a formal secret.
- **`atmos secret`** requires a secret to be **declared** under a component's `secrets.vars` before
  it can be set or read, and only operates on stores marked `secret: true`. Use it for values that
  should be tracked, scoped (`instance`/`stack`/`global`), and resolved via the `!secret` YAML
  function.

Writing to a `secret: true` store with `atmos store set` (or the `type: store` workflow step) is
allowed — for example, to write a generated password — but it bypasses `atmos secret`'s
declaration and scope tracking. Prefer `atmos secret` when a value should be declared and tracked
as a secret.

## Stack and component scoping

`--stack` and `--component` are **optional** for every `atmos store` subcommand. A key set with
both scopes a value the same way [`atmos secret`](/cli/commands/secret/usage) does; a key set with
neither is a store-global value:

```shell
# Scoped to a stack and component
atmos store set app-metadata image_tag sha256:abc123 --stack=prod --component=ecs-service

# Store-global (no stack/component)
atmos store set app-metadata shared_config '{"region":"us-east-1"}'
```

`atmos store get`/`delete` must use the **same** `--stack`/`--component` (or lack thereof) as the
`set` that wrote the value — the stack/component pair is part of how the underlying key is
composed.
