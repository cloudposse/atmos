<Intro>
Print temporary AWS credentials for any Atmos identity in the JSON format that the AWS CLI and AWS SDKs expect from a [`credential_process`](https://docs.aws.amazon.com/sdkref/latest/guide/feature-process-credentials.html) profile. Point a profile in `~/.aws/config` at this command and tools such as `aws`, `boto3`, or the Terraform AWS provider can use your Atmos identities from any directory, without wrapping each call in `atmos auth exec`.
</Intro>

## Usage

```shell
atmos aws credential-process --identity=<name> [--min-validity=15m]
```

The same output is available through `atmos auth env`:

```shell
atmos auth env --format=credential-process --identity=<name>
```

## Examples

```shell
# Print credentials for an identity
atmos aws credential-process --identity=app-sandbox-1

# Refresh credentials that expire within the next 30 minutes
atmos aws credential-process --identity=app-sandbox-1 --min-validity=30m

# Pretty-print the result
atmos aws credential-process --identity=app-sandbox-1 | jq .

# Equivalent output through the auth env alias
atmos auth env --format=credential-process --identity=app-sandbox-1
```

## Using Atmos Identities from the AWS CLI

Add a profile to `~/.aws/config` whose `credential_process` calls Atmos. The AWS CLI runs that command each time it needs credentials.

```ini title="~/.aws/config"
[profile app-sandbox-1]
credential_process = atmos --chdir=/path/to/infrastructure aws credential-process --identity=app-sandbox-1
region = us-east-1
```

Then use the profile from any directory:

```shell
aws sts get-caller-identity --profile=app-sandbox-1
aws s3 ls --profile=app-sandbox-1
```

Atmos locates `atmos.yaml` the usual way, so you can pick whichever of these fits your setup:

<dl>
  <dt>`--chdir=/path/to/project` <em>(alias `-C`)</em></dt>
  <dd>
    The most robust option. Atmos behaves exactly as if you ran the command from the project directory, so relative paths in `atmos.yaml` resolve as expected.

    ```ini title="~/.aws/config"
    credential_process = atmos --chdir=/path/to/infrastructure aws credential-process --identity=app-sandbox-1
    ```
  </dd>

  <dt>`--config-path=/path/to/project`</dt>
  <dd>
    Point Atmos at the directory that contains `atmos.yaml`.

    ```ini title="~/.aws/config"
    credential_process = atmos --config-path=/path/to/infrastructure aws credential-process --identity=app-sandbox-1
    ```
  </dd>

  <dt>`ATMOS_CLI_CONFIG_PATH`</dt>
  <dd>
    Set the environment variable in the shell that runs `aws`, and keep the profile short.

    ```shell
    export ATMOS_CLI_CONFIG_PATH=/path/to/infrastructure
    ```

    ```ini title="~/.aws/config"
    credential_process = atmos aws credential-process --identity=app-sandbox-1
    ```
  </dd>

  <dt>Global `~/.atmos/atmos.yaml`</dt>
  <dd>
    Define the identities in the global Atmos configuration. No path flags are needed because Atmos finds the file from any directory.
  </dd>
</dl>

:::tip Windows paths
Quote any path that contains spaces, for example `credential_process = atmos --chdir="C:\Users\me\My Project" aws credential-process --identity=app-sandbox-1`.
:::

## How It Works

1. Atmos resolves the identity from `--identity`, then the `ATMOS_IDENTITY` environment variable, then the default identity in `atmos.yaml`. Interactive identity selection is not available because the AWS CLI captures the command's output.
2. If cached credentials for the identity expire later than `--min-validity` from now (default 15 minutes), Atmos prints them immediately without any network call. The AWS CLI runs `credential_process` once per CLI invocation, so reusing valid credentials keeps every `aws` command fast.
3. Otherwise Atmos authenticates the identity the same way [`atmos auth login`](/cli/commands/auth/login) would, then prints the new credentials.
4. Atmos prints exactly one JSON document to stdout. Logs and notices go to stderr, so they never corrupt the output the AWS CLI parses.

When the identity needs an interactive login that cannot happen while the AWS CLI owns the terminal, such as an expired AWS SSO session, the command fails with a hint. Run [`atmos auth login`](/cli/commands/auth/login) first, then retry the `aws` command.

```shell
atmos auth login --identity=app-sandbox-1
aws s3 ls --profile=app-sandbox-1
```

## Output Contract

The command prints one line of JSON in the [AWS process-credential format](https://docs.aws.amazon.com/sdkref/latest/guide/feature-process-credentials.html):

```json
{"Version":1,"AccessKeyId":"ASIA...","SecretAccessKey":"...","SessionToken":"...","Expiration":"2026-10-02T18:30:00Z"}
```

- The version field, `Version`, is always `1`.
- Both `AccessKeyId` and `SecretAccessKey` are always present.
- Long-lived keys omit `SessionToken` and `Expiration`.
- The expiration is an RFC3339 timestamp in UTC.

The credentials are printed unmasked because delivering them to the caller is the purpose of the command. Secret masking still applies to all other Atmos output.

## Flags

<dl>
  <dt>`--identity` <em>(alias `-i`)</em></dt>
  <dd>
    Name of the identity to print credentials for. If omitted, Atmos uses the `ATMOS_IDENTITY` environment variable, then the default identity configured in `atmos.yaml`. The identity must be an AWS identity.
  </dd>

  <dt>`--min-validity`</dt>
  <dd>
    Minimum remaining lifetime for cached credentials to be reused. When the cached credentials expire sooner than this, Atmos authenticates again before printing. Default: `15m`. Accepts durations such as `30m` or `1h`. Environment variable: `ATMOS_AWS_CREDENTIAL_PROCESS_MIN_VALIDITY`.
  </dd>
</dl>

## Using Credential Helpers with Atmos

This command produces credentials for the AWS CLI. The opposite direction, running an existing external helper such as `okta-aws-cli` or `aws-vault` and using its credentials in Atmos, is handled by the [`aws/credential-process`](/cli/configuration/auth/identities#credential-process) identity kind. The two combine: Atmos can run your helper, then hand the credentials to the AWS CLI through this command.

## Troubleshooting

<dl>
  <dt>Verify the profile</dt>
  <dd>
    Run `aws sts get-caller-identity --profile=app-sandbox-1`. If it prints the expected account and role, the profile is wired correctly.
  </dd>

  <dt>Run the command directly</dt>
  <dd>
    Run `atmos --chdir=/path/to/infrastructure aws credential-process --identity=app-sandbox-1` in a terminal to see any error output the AWS CLI would otherwise hide.
  </dd>

  <dt>The command asks you to log in</dt>
  <dd>
    The identity's session expired. Run `atmos auth login --identity=app-sandbox-1`, then retry.
  </dd>

  <dt>Recursion error</dt>
  <dd>
    A `credential_process` helper called back into Atmos for an identity that was already being resolved. This happens when an `aws/credential-process` identity runs `atmos aws credential-process --identity=<itself>`. Point the helper at a different identity.
  </dd>

  <dt>Atmos cannot find atmos.yaml</dt>
  <dd>
    The AWS CLI runs the command from your current directory. Add `--chdir=/path/to/infrastructure` to the profile, or use one of the other [configuration discovery options](#using-atmos-identities-from-the-aws-cli).
  </dd>
</dl>
