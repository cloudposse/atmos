<Intro>
Move an existing CloudFormation deployment from Rain or the AWS CLI to Atmos.
Keep your CloudFormation templates and deployed stacks, and describe their
parameters, regions, and authentication in Atmos stack manifests.
</Intro>

<Experimental />

## Why This Guide?

[Rain is deprecated and archived](https://github.com/aws-cloudformation/rain).
Existing releases remain available, but the project no longer plans fixes or
new releases.

Atmos provides CloudFormation deployment commands and stack configuration.
It does not interpret Rain directives or its full configuration format.
You can import the `Parameters` and `Tags` sections of a Rain configuration file.

## Migration Overview {#crawl-walk-run}

1. Identify the existing stack's name, AWS account, and region.
2. Resolve Rain-specific template directives and package local assets.
3. Configure the template and parameters in Atmos.
4. Preview the changes, apply them, and verify the deployed outputs.

## Migrate a Stack {#crawl-get-running-in-20-minutes}

### Prerequisites {#what-youre-going-to-do}

- A CloudFormation template and its parameter values.
- Access to the AWS account and region containing the existing stack.
- The existing CloudFormation stack name, if migrating a deployed stack.

The examples use component `vpc`, Atmos stack `dev`, and CloudFormation stack
`acme-plat-dev-vpc`. Replace these values with your deployment's names.

### Step 1: Install Atmos

```shell
brew install atmos
```

See [Installation](/install) for other platforms and installation methods.
Configure an [Atmos identity](/stacks/auth) for the existing AWS account, or use
your existing AWS SDK credentials. For an AWS profile, set `AWS_PROFILE` in the
shell where you run Atmos.

### Step 2: Resolve `!Rain::` Directives (If Any)

Skip this step for plain CloudFormation templates. Atmos sends templates
referenced by `path` as written; Rain directives must be resolved first.

The following table covers common directives. See
[Rain's packaging reference](https://github.com/aws-cloudformation/rain/blob/main/docs/rain_pkg.md)
for supported Rain syntax.

| Directive | Migration approach | Limitation |
|---|---|---|
| `Constant` | Replace scalar constants with CloudFormation parameters or literal values. | Preserve the original value and type. |
| `Env` | Supply a parameter through Atmos [`!env`](/functions/yaml/env). | This belongs in stack configuration, not a `path` template. |
| `Include` | Expand the YAML/JSON fragment before deployment, or compose an inline Atmos template with [`!include`](/functions/yaml/include). | Atmos does not process `!Rain::Include` in files. |
| `Embed` | Insert small file contents as a YAML block scalar. | Build and upload larger assets separately. |
| `S3`, `S3Http` | Upload the asset and use its S3 URI, HTTPS URL, or bucket/key fields. | Atmos template packaging does not upload local assets. |
| `Module` | Expand modules into a plain CloudFormation template using the existing build process. | Atmos does not implement Rain's module system. |

#### Example: Environment Values {#beforeafter-constantenv--parameters}

A file-based template uses standard CloudFormation parameters:

<File title="components/cloudformation/vpc/template.yaml">
```yaml
AWSTemplateFormatVersion: '2010-09-09'
Parameters:
  CidrBlock:
    Type: String
Resources:
  VPC:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: !Ref CidrBlock
Outputs:
  VpcId:
    Value: !Ref VPC
```
</File>

The corresponding Atmos component can read the value from the environment:

```yaml
parameters:
  CidrBlock: !env VPC_CIDR
```

Use your existing template for migration. The minimal template above illustrates
parameter syntax; it is not a replacement for an existing VPC template.

#### Example: Embedded Files {#beforeafter-embed--inline-block-scalar}

Replace `ZipFile: !Rain::Embed handler.py` with the file's contents:

```yaml
Code:
  ZipFile: |
    def handler(event, context):
        return {"statusCode": 200}
```

This is a fragment of a Lambda resource. Retain its other required properties.
For separately packaged code, use an uploaded artifact's S3 bucket and key.

### Step 3: Create Minimal atmos.yaml

<File title="atmos.yaml">
```yaml
base_path: .
components:
  "aws/cloudformation":
    base_path: components/cloudformation
stacks:
  base_path: stacks
  included_paths:
    - "deploy/**/*"
```
</File>

Keep the existing template under `components/cloudformation/vpc/template.yaml`,
or set `base_path` to its current component parent directory.

### Step 4: Create Your First Stack

<File title="stacks/deploy/dev.yaml">
```yaml
name: dev
components:
  "aws/cloudformation":
    vpc:
      path: template.yaml
      stack_name: acme-plat-dev-vpc
      settings:
        aws_cloudformation:
          region: us-east-1
      parameters:
        CidrBlock: "10.0.0.0/16"
```
</File>

For an existing deployment, match its `stack_name`, AWS account, region, and
parameter values. A different name, account, or region selects a different
stack and may create a new one. Configure the existing capabilities, tags,
service role, and stack policy when applicable.

#### Import Parameter Files

An AWS CLI parameter array can be included directly:

<File title="params/dev-parameters.json">
```json
[
  {"ParameterKey": "CidrBlock", "ParameterValue": "10.0.0.0/16"}
]
```
</File>

In the component declared in `stacks/deploy/dev.yaml`, replace `parameters` with:

```yaml
parameters: !include ../../params/dev-parameters.json
```

To retain a deployed parameter on update, the list form accepts
`UsePreviousValue: true` without `ParameterValue`. See
[Parameters](/stacks/components/aws-cloudformation#parameters).

#### Import Rain Configuration Sections

<File title="params/rain-config.yaml">
```yaml
Parameters:
  CidrBlock: 10.0.0.0/16
Tags:
  Team: platform
```
</File>

Select each section explicitly in the Atmos component:

```yaml
parameters: !include ../../params/rain-config.yaml .Parameters
tags: !include ../../params/rain-config.yaml .Tags
```

Paths are relative to the stack file. Importing the whole Rain configuration
as `parameters` is invalid because its top-level values are maps.
Atmos does not automatically read Rain's `RAIN_VAR_*` or `RAIN_DEFAULT_TAG_*`
variables; declare those values in stack configuration.

### Step 5: Run Atmos

Check static configuration first:

```shell
atmos aws cloudformation plan vpc -s dev --dry-run
```

Then preview against the existing AWS stack:

```shell
atmos aws cloudformation plan vpc -s dev
```

The real preview authenticates, creates a changeset, displays it, and removes
it. If the template exceeds the inline size limit, configure and create the
[artifact bucket](#4-provisioning-the-artifact-bucket) before this step.

Review replacements, deletions, and parameter changes before applying:

```shell
atmos aws cloudformation apply vpc -s dev
atmos aws cloudformation output vpc -s dev
```

Apply creates a fresh changeset and prompts before executing it. For automation,
use `deploy` or `apply --auto-approve`. Use
[explicit changesets](#changesets-managed-explicitly) when review and execution
must use the same saved changeset.

If using Atmos Auth, pass the same `--identity` to preview, apply, and output.
Confirm that the outputs and stack resources match the intended deployment.
The `cfn` alias works in place of `cloudformation`.

## Configuration Changes {#what-just-happened}

### Key Differences at a Glance

| Setting | Rain workflow | Atmos configuration |
|---|---|---|
| Stack name | Command argument | Component `stack_name` |
| Parameters and tags | Flags or Rain configuration file | `parameters` and `tags`, with optional `!include` |
| Region | Rain `--region` | `settings.aws_cloudformation.region` |
| Credentials | Rain `--profile` | Atmos Auth or the AWS SDK credential chain |
| Artifact bucket | Rain-managed bucket | An S3 delivery target, provisioned explicitly or automatically |
| Environments | Separate invocations | Stack manifests with imports and inheritance |

### What Stays The Same

Plain CloudFormation resources and intrinsic functions remain valid in
file-based templates. An existing stack stays in CloudFormation; no Terraform
state import is needed.

### What You Added

The `atmos.yaml` file defines component and stack locations. Stack manifests
hold the per-environment deployment settings.

## Common Tasks {#walk-immediate-value}

### Rain Command Comparison {#1-rain--atmos-verb-cross-reference}

Command names do not always imply equivalent behavior. These comparisons use
[Rain's command reference](https://github.com/aws-cloudformation/rain/tree/main/docs).

| Rain command | Atmos command or approach | Difference |
|---|---|---|
| `rain deploy` | [`apply`](/cli/commands/aws/cloudformation/apply) or [`deploy`](/cli/commands/aws/cloudformation/deploy) | `apply` prompts; `deploy` auto-approves. |
| `rain deploy --no-exec` | [`changeset create`](/cli/commands/aws/cloudformation/changeset/create) | Leaves a named changeset for review. |
| `rain deploy --changeset` | [`changeset execute`](/cli/commands/aws/cloudformation/changeset/execute) | Executes the named changeset. |
| `rain diff` | [`diff` / `plan`](/cli/commands/aws/cloudformation/diff) for deployment previews | Rain compares templates; Atmos creates a changeset against AWS. |
| `rain fmt` | [`fmt`](/cli/commands/aws/cloudformation/fmt) | Formats YAML in place; `--check` verifies formatting. |
| `rain cat` | [`get template`](/cli/commands/aws/cloudformation/get/template) | Use `--original` for the submitted template. |
| `rain ls` | [`list`](/cli/commands/aws/cloudformation/list) | Adds managed/unmanaged annotations from Atmos configuration. |
| `rain logs` | [`logs`](/cli/commands/aws/cloudformation/logs) | Includes nested-stack events; `--chart` shows a resource timeline. |
| `rain watch` | [`watch`](/cli/commands/aws/cloudformation/watch) | Watches an existing stack operation. |
| `rain tree` | [`tree`](/cli/commands/aws/cloudformation/tree) for deployed nested stacks | Rain graphs dependencies in a local template; Atmos shows deployed nested stacks. |
| `rain rm` | [`delete`](/cli/commands/aws/cloudformation/delete) | Prompts and respects termination protection. |
| `rain bootstrap` | [`backend create`](/cli/commands/aws/cloudformation/backend/create) | Uses the component's configured S3 target. |
| `rain pkg` | [Archive and upload hooks](/stacks/components/aws-cloudformation#asset-packaging-hooks) | Configure the asset upload and template references explicitly. |
| `rain forecast` | No equivalent | Atmos `validate` and `plan` do not reproduce Rain's resource-specific failure predictions. |
| `rain build`, `rain module`, `rain merge` | Keep an authoring/build step that emits plain CloudFormation | No Rain-compatible authoring commands. |
| `rain cc` | No equivalent | No Cloud Control passthrough. |

### Read Stack Outputs {#2-outputs-on-demand}

```shell
atmos aws cloudformation output vpc -s dev
atmos aws cloudformation output vpc VpcId -s dev
```

Other components can read an output through
[`!aws.cloudformation.output`](/functions/yaml/aws.cloudformation.output):

```yaml
parameters:
  VpcId: !aws.cloudformation.output vpc VpcId
```

The producer must already be deployed. For cross-account lookups, configure
its [default direct target identity](/stacks/components/aws-cloudformation#output-references).

### Detect Drift {#3-drift-detection-as-a-first-class-verb}

```shell
atmos aws cloudformation drift detect vpc -s dev --fail-on-drift
atmos aws cloudformation drift describe vpc -s dev
```

### Provision an Artifact Bucket {#4-provisioning-the-artifact-bucket}

Add an S3 delivery target to the component:

```yaml
provision:
  targets:
    artifacts:
      kind: aws/s3
      bucket: acme-plat-cfn-artifacts
      region: us-east-1
```

Choose a bucket name available to your account, then create it before previewing
or deploying an oversized template:

```shell
atmos aws cloudformation backend create vpc -s dev
```

Alternatively, set `provision.backend.enabled: true` alongside `targets` to let
`apply`/`deploy` create a missing bucket. Preview and validation commands do not
create it. See [automatic bucket provisioning](/stacks/components/aws-cloudformation#automatic-bucket-provisioning).

### Template Packaging and Local Assets {#s3-packaging-is-size-triggered-not-asset-aware}

Atmos uploads the template body to S3 when it exceeds 51,200 bytes. This does
not replace `rain pkg` or `aws cloudformation package`, which can upload assets
referenced by a template.

Atmos can build Lambda archives with the [`archive` step](/steps/type/archive).
Run it in a CloudFormation lifecycle hook, then upload with the
[`publish` step](/steps/type/publish). See the
[asset-packaging hook example](/stacks/components/aws-cloudformation#asset-packaging-hooks).

For nested templates, upload the template files and set their `TemplateURL`
references explicitly. S3 delivery targets handle the parent template upload;
they do not discover local assets or rewrite references. The `publish` step
with an `aws/s3` target uploads explicitly selected files and directories
without rewriting templates.

## Additional Workflows {#run-when-youre-ready}

### StackSets

Configure an [AWS StackSet target](/stacks/components/aws-cloudformation#stackset-targets)
before running:

```shell
atmos aws cloudformation stackset create vpc -s dev
atmos aws cloudformation stackset instances vpc -s dev
```

Instance targeting supports self-managed permissions. Review the
[StackSet limitations](/cli/commands/aws/cloudformation/stackset/create#behavior)
before migrating a service-managed deployment.

### Changesets for Separate Review and Deployment {#changesets-managed-explicitly}

```shell
atmos aws cloudformation changeset create vpc -s dev
atmos aws cloudformation changeset execute vpc -s dev --changeset-name <name>
```

Use the changeset name returned by `create`. Unlike `plan`, this preserves the
changeset for later execution.

### Component Inheritance and Catalogs

Move shared configuration into a catalog component and inherit it in each
stack. See [Component Inheritance](/howto/inheritance).

## Migration Benefits {#why-its-worth-it}

### Shared Deployment Configuration {#real-benefits-youll-feel-immediately}

Atmos provides reusable stack manifests, environment-specific parameters,
output references, and dependency ordering across component types. Start with
one stack, then add inheritance and bulk operations as needed.

## Compatibility Limits {#what-atmos-wont-do}

- Rain directives and modules require preprocessing outside Atmos.
- Local assets use explicit archive/upload hooks or workflow steps; template references are configured explicitly.
- Rain configuration sections must be imported explicitly.
- Rain `diff`, `tree`, and `forecast` have different semantics from Atmos previews,
  nested-stack inspection, and validation.

## Migration Checklist

<TaskList>
- [ ] Install Atmos and configure credentials.
- [ ] Match the existing stack name, AWS account, and region.
- [ ] Resolve Rain directives and upload local assets.
- [ ] Configure the template, parameters, capabilities, tags, and any service role or policy.
- [ ] Create an artifact bucket if the template needs packaging.
- [ ] Run static dry-run, then inspect a real plan.
- [ ] Apply after reviewing changes.
- [ ] Verify outputs and deployed resources.
- [ ] Repeat for the remaining environments.
</TaskList>

## Common Questions

<FAQItem question="Do I need to change my CloudFormation templates?">
Plain CloudFormation templates can be used as files. Resolve Rain directives
and local asset references before deploying. Use an inline Atmos template when
you need stack templating or YAML functions inside the template.
</FAQItem>

<FAQItem question="Can I keep using my parameters JSON file?">
Yes. Include an AWS CLI parameter array directly. For a Rain configuration file,
select `.Parameters`, and import `.Tags` separately when needed.
</FAQItem>

<FAQItem question="Is there a Rain CLI compatibility mode?">
No. Use the command comparison above to update scripts, including their flags,
confirmation behavior, and handling of output.
</FAQItem>
