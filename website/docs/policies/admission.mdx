<Intro>
Use admission policies to reject YAML function execution and CLI commands, or attach command
restrictions to component instances using literal tags and labels.
</Intro>

## Input kinds

| Kind | Gate | Input fields | Instance selectors |
|---|---|---|---|
| `function` | Before a YAML function handler executes, including configuration loading | `name`: canonical name without `!` | No; instance metadata may not exist yet |
| `command` | Before a runnable CLI command's argument validator and pre-run hooks | `command`: command path string; `path`: array of command names, excluding `atmos` | No |
| `component.command` | During shared stack resolution, before component template/function evaluation and tool execution | `command`, `component_type`, `component`, `stack`, `dry_run`, `capabilities` | Yes; literal inherited metadata |

These gates do not require `--affected`. Function arguments and CLI argument/flag values are not
exposed: they can contain secrets. All three kinds support CEL and restricted Starlark, denial,
and [GitHub approval requirements](/policies/approvals).

## Disable `!exec`

```yaml title="policy.d/no-exec.yaml"
apiVersion: atmos/v1
kind: Policy
metadata:
  name: no-exec
  description: Prevent configuration from executing shell commands through !exec.
spec:
  policies:
    disable:
      on: function
      action: deny
      rule: input.name == 'exec'
```

The check applies to `atmos.yaml` mappings and sequences, stack YAML functions, and registry-based
lazy evaluation. Skipped functions are not executed. Literal text containing `!exec` is not shell
execution. This rule does not disable shell hooks, automation scripts, external tools, or Go-template
functions; those are different execution mechanisms, not aliases for the YAML `!exec` function.

## Block a command

```yaml
apiVersion: atmos/v1
kind: Policy
metadata:
  name: no-destroy
spec:
  policies:
    direct-destroy:
      on: command
      action: deny
      rule: input.command == 'terraform destroy'
```

CLI admission covers registered and custom runnable commands, including commands without components
or stacks. Native aliases use the canonical command path. Built-in commands are also checked before
project initialization and configuration loading. Configuration is loaded to register custom
commands before their CLI admission; use function policies to control YAML execution during that loading.
Help rendering and external programs invoked without Atmos are not command admission targets.

## Attach to instances

```yaml
apiVersion: atmos/v1
kind: Policy
metadata:
  name: production
spec:
  policies:
    no-delete:
      on: component.command
      match:
        labels: {stage: prod}
      action: deny
      rule: input.command in ['delete', 'destroy']
```

Shared stack resolution applies this gate to Terraform, Helmfile, Helm, Kubernetes, Packer, Ansible,
container, emulator, and custom component integrations using that resolver. Commands without an
instance still receive CLI admission, not fabricated component metadata. An integration bypassing
shared stack resolution must add instance admission before advertising that capability.

Metadata used by selectors must be literal: unresolved templates/functions or malformed metadata
produce an error, not a non-match. `capabilities` always includes `component.command` and `function`;
Terraform also supplies `terraform.plan` and `operation`, while Helmfile, Helm, and Kubernetes supply
`operation`. A capability name does not manufacture its input at other gates.

## Enforcement configuration

The CLI loads and pins policy definitions after applying `--chdir`, before configuration loading.
Later configuration changes to the environment or working directory do not replace that in-memory
bundle. Missing default `policy.d/` remains opt-in behavior; protect an explicit `ATMOS_POLICY_DIR`
and the governing files in CI. Pinning does not establish trust in files selected from the PR itself.

Denials, evaluation failures, missing required inputs, and outstanding approvals return errors.
Dry-run does not bypass admission. See [enforcement](/policies/configuration#enforcement) for repository
protection requirements and [affected policies](/policies/affected) for semantic detachment checks.
