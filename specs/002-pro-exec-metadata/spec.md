# Feature Specification: Atmos Pro Command-Execution Metadata Upload

**Feature Branch**: `1199-pro-exec-metadata`

**Created**: 2026-08-11

**Status**: Draft

**Input**: User description: "Add Atmos Pro command-execution metadata upload. When Atmos detects it is running in CI AND Atmos Pro is configured, every atmos command execution sends metadata to a new Atmos Pro API endpoint POST /v1/atmos/exec. Payload includes a base envelope (version, OS, arch, command, args, exit code, git info), resource usage metrics (wall time, CPU time, peak memory, page faults, context switches, block I/O), and per-command additional structured JSON data (e.g. terraform plan/apply attaches created/updated/deleted/replaced resources, outputs, warnings/errors, and per-component logs). Delivery is synchronous and blocking for a hardcoded allowlist of commands (terraform plan/apply, describe affected) and asynchronous/fire-and-forget for all other commands, with both the sync/async choice and the strict/best-effort failure behavior decided per-command in code, not via user-facing settings. Testing requirement: extend the existing local-only Pact consumer contract test suite with a 9th interaction for POST /v1/atmos/exec covering the full payload shape, so the generated contract can be handed to the Atmos Pro team to implement the provider side."

## Clarifications

### Session 2026-08-11

- Q: For asynchronous (fire-and-forget) commands, should the CLI process wait briefly to ensure the upload has at least been dispatched before exiting, or exit immediately with no delivery guarantee? → A: Short bounded wait — best-effort flush with a small timeout before exiting, to maximize delivery without materially slowing the command.
- Q: For synchronous commands (`terraform plan`, `terraform apply`, `describe affected`), how long should Atmos wait for the execution-record upload to be confirmed before treating delivery as failed? → A: A moderate default ceiling (~10 seconds), consistent with typical HTTP client timeout conventions, and this default MUST be user-configurable (increasable) via Atmos configuration.
- Q: Should a failed asynchronous execution-metadata upload ever be visible to the user, or remain completely silent by default? → A: Silent by default; only surfaced at debug/verbose log level, consistent with existing telemetry failure handling.
- Q: Should each execution record carry a unique identifier for correlation (CI run, dedup, related records)? → A: Yes — reuse the existing Atmos Pro run identifier already used by other Pro uploads, rather than inventing a new ID scheme.
- Q: When an execution record's command-specific structured data is too large for a single request, what should be chunked/batched across multiple correlated requests? → A: Only the command-specific structured-data field is split across multiple correlated requests, reusing the existing chunked-upload/batch-correlation mechanism already used for `describe affected` uploads; the base envelope and resource-usage metrics are small and are always sent in full, never truncated or dropped.
- Q: For synchronous commands, does the ~10s upload-confirmation wait (FR-008a) apply per chunk or to the whole record? → A: To the whole record (all chunks combined), ~10s total, not per chunk.

### Session 2026-08-18

- Q: For a command on the synchronous allowlist (`terraform plan`, `terraform apply`, `describe affected`), should the async default-path upload (FR-002/FR-009) still also fire, or should sync delivery replace it for that invocation? → A: Mutually exclusive — sync-allowlisted commands are exempted from the async default path entirely; each qualifying invocation produces exactly one execution record, delivered via its command's classified path (sync or async), never both.
- Q: For a multi-component `atmos terraform plan --affected`/`--all` run (many components in one CLI invocation), should each per-component graph node produce its own execution record, or should the invocation produce one aggregate record? → A: Aggregate — one execution record per CLI invocation; per-component results (including each component's identity, outcome, and structured data) are folded into that single record's structured data, not sent as separate records.
- Q: Should `atmos terraform deploy` (which already has the same CI-mode stdout-capture wiring as `plan`/`apply`) join the synchronous execution-record allowlist, or stay outside it? → A: Add `deploy` to the synchronous allowlist alongside `plan`/`apply`/`describe affected`.
- Q: Since `terraform deploy` typically wraps plan+apply internally, should its execution record carry deploy's own structured infrastructure-change data (FR-006), or just the base envelope like `describe affected`? → A: `deploy` gets structured infrastructure-change data too, same as `plan`/`apply` — FR-006 extended to include it.
- Q: For a `terraform plan`/`apply` invocation where the pre-existing `uploadStatus`/`--upload-status` PATCH mechanism (`internal/exec/pro.go`, `PATCH .../instances`) also fires — independently of this feature's `POST /v1/atmos/exec` — should the client coordinate/merge the two paths, or remain fully independent? → A: Remain independent — the Atmos Pro backend owns any cross-record correlation/dedup between the two record types; the Atmos client MUST NOT merge, skip, or make the two paths mutually exclusive. The one client-side guarantee is that the `Command` and `Args` values reported by the new execution record MUST be correlatable with what `uploadStatus` reports for the same invocation, so Atmos Pro can correlate the two records by content even without a shared record ID.
- Q: `InstanceStatusUploadRequest.Command` is a bare subcommand (`"plan"`) and has separate `Component`/`Stack` fields with no `Args` counterpart, while `ExecUploadRequest.Command` was `cmd.CommandPath()` (`"atmos terraform plan"`) with a separate, currently-always-empty `Args` field — what concrete `Command`/`Args` shape should `ExecUploadRequest` use so the two paths are correlatable? → A: `ExecUploadRequest.Command` MUST be the subcommand path without the `atmos` root (e.g. `"terraform plan"`, not `"atmos terraform plan"`). `ExecUploadRequest.Args` MUST hold only the positional arguments (e.g. the component identifier: `["cdn"]`), replacing the current always-empty `Args`. A new, separate `ExecUploadRequest.Flags` field MUST hold the CLI flags actually passed (e.g. `["-s", "plat-use2-dev", "--upload-status"]`), each passed through the existing secret-masking (FR-010) — positional args and flags are kept in distinct fields, not combined into one array.

### Session 2026-08-19

- Q: `FR-003b`'s own worked example includes `--upload-status` in the reported `Flags` (`["-s", "plat-use2-dev", "--upload-status"]`), but the current implementation strips `--upload-status` before the execution record is built, treating it as "internal only" — this contradiction is the confirmed root cause of a production report where `Flags` came back empty. Should `--upload-status` (and other atmos-recognized flags) be included in the reported `Flags`, or excluded as internal-only? → A: Include `--upload-status` (and every other atmos-recognized flag) in `Flags` — report exactly what the user typed, with no exclusions. `Flags` MUST be derived from the invoking command's actually-set flags (e.g. via the CLI framework's own record of which flags were explicitly passed), never from a leftover/pass-through-args slice that never contained atmos-recognized flags to begin with.
- Q: The async delivery path's current implementation (`commandArgsAndFlags`, `pkg/proexec/async.go`) serializes every flag as a `--name value` pair, even for boolean flags with no value (e.g. `--upload-status` → `["--upload-status", "true"]`), which conflicts with the spec's own worked example showing bare tokens as typed (`["-s", "plat-use2-dev", "--upload-status"]`, no trailing `"true"`). Which wire shape should `Flags` use? → A: Bare tokens as typed by the user — a boolean/valueless flag like `--upload-status` MUST appear alone, with no synthesized value appended, matching the literal command line. The async path's current `--name value`-pair-for-every-flag serialization is now the outlier and MUST be changed to match, not the spec's example.
- Q: After implementing the above, real-world testing found `Flags` still doesn't literally match "as typed" in two ways: shorthand flags are reported by their canonical long name (`atmos terraform plan -s plat-use2-dev --upload-status` reports `--stack`, not `-s`), and flag order follows Cobra's internal iteration order (alphabetical by flag name) rather than invocation order (e.g. `--upload --logs-level Debug` typed is reported as `--logs-level Debug --upload`). Both are structural: Cobra's parsed flag set (`cmd.Flags().Visit()`) never records which alias was typed or in what order, so literal reconstruction would require parsing raw pre-parse command-line tokens instead — a materially larger change. Should `Flags` be changed to preserve exact shorthand/order (requiring raw-token parsing), or is the current canonical-long-form / Cobra-iteration-order behavior acceptable? → A: Current behavior is acceptable — drop the "exactly as typed" requirement for shorthand form and ordering. `Flags` MUST use each flag's canonical long name (e.g. `--stack`, never `-s`) and MAY appear in any order (Cobra's own flag-iteration order, not necessarily invocation order); no raw-token parsing is required. The no-synthesized-value rule for boolean flags (previous Q&A) is unaffected and still applies.
- Q: Should each execution record also carry a new, freshly-generated UUID that uniquely identifies that single execution — separate from the existing Atmos Pro run identifier (FR-003) which correlates records across a CI run — and if so, what is it called and how does it relate to chunk correlation (FR-011)? → A: Yes. Add a new `ExecutionID` field (a fresh UUID v4 generated once per qualifying command invocation) alongside the existing Atmos Pro run identifier — the run identifier still correlates records across a CI run, while `ExecutionID` uniquely identifies this one execution record. `ExecutionID` also replaces the ad hoc chunk-correlation tag from FR-011: when a record's structured data is split across multiple correlated requests, all chunks of that record are tagged with the same `ExecutionID` so Atmos Pro can reassemble them.
- Q: The multi-chunk `DataItems`/`BatchID`/`BatchIndex`/`BatchTotal` splitting model (previous FR-011) is being replaced — batching now applies only to the `Data` field, which becomes one of two shapes (inline JSON, or a string URL to a stored blob). What size threshold decides which shape is used, and is it measured against `Data` alone or the whole payload? → A: A fixed (not user-configurable) 4 MB threshold, measured against the total marshaled size of the whole execution-record payload (base envelope + resource-usage metrics + `Data` combined) — not `Data` in isolation.
- Q: When `Data` must be uploaded out-of-band (payload at or above the 4 MB threshold), does the new `POST /v1/atmos/exec/data` upload ever need its own client-side chunking for extremely large `Data`, or is it always exactly one request? → A: Always exactly one request — the blob store (Vercel Blob) handles arbitrarily large uploads in a single call. This fully retires the old `DataItems`/`BatchID`/`BatchIndex`/`BatchTotal` chunked-request model; there is no longer any multi-request splitting anywhere in this feature.
- Q: For asynchronous (fire-and-forget) commands, when the `POST /v1/atmos/exec/data` upload is required before the main `POST /v1/atmos/exec` call can be built, does that data-upload step get its own timing allowance, or does it count against the existing ~2s async bounded-flush window (FR-009)? → A: Counts against the same ~2s window — the whole sequence (data upload, if needed, then the main upload) must fit inside the existing async bounded-flush ceiling; if it can't complete in time, the record is dropped silently, per existing FR-009a, same as any other async delivery failure.
- Q: For synchronous commands, does the `POST /v1/atmos/exec/data` upload's time count toward the same ~10s total sync wait ceiling (FR-008a) as the main `POST /v1/atmos/exec` call, or does it get a separate budget? → A: Counts toward the same ~10s total — both the data upload (if needed) and the main call together must complete within the existing ~10s (user-configurable) ceiling, consistent with the prior "whole record, not per chunk" timing rule.
- Q: What field name should carry the `ExecutionID` on the new `POST /v1/atmos/exec/data` request, to key/correlate it with the corresponding main execution record? → A: `execution_id` (snake_case), matching the correlation field's role of coupling the two requests for the same execution.

### Session 2026-08-21

- Q: A fresh code trace found `TerraformExecData.exit_code` (FR-006) is frequently `0`/uninformative in production even when a plan has real changes, for two independent reasons: (1) `terraform plan` only returns a meaningful non-zero code with `-detailed-exitcode`, and Atmos only adds that flag when the legacy `--upload-status` flag is passed (`internal/exec/terraform_execute_helpers_args.go:38-40`) — unrelated to whether exec-metadata capture is active; (2) even when `-detailed-exitcode` is used, CI-mode's `mapCIExitCode` (`internal/exec/ci_exit_codes.go:12-16`) remaps exit code 2 ("changes detected") to success/`nil` before `captureExecMetadataSync` ever reads it (`internal/exec/terraform_execute_helpers_exec.go:456-471`), discarding the real signal. Should `-detailed-exitcode` be decoupled from `--upload-status` and made unconditional for exec-metadata capture, and should the pre-CI-remap exit code be what's captured for `TerraformExecData.exit_code`? → A: Yes — `-detailed-exitcode` MUST be added to `plan` (and to the internal `apply`/`deploy` invocation, consistent with FR-006's existing per-invocation `exit_code` semantics) whenever exec-metadata capture is active, independent of `--upload-status`. `TerraformExecData.exit_code` MUST be the terraform/tofu subprocess's real, pre-CI-remap exit code — captured before `mapCIExitCode`'s CI-mode remapping is applied to what the Atmos CLI itself returns/exits with. The remap MAY still determine Atmos's own process exit code (base envelope's `exit_code`, FR-003) for CI-friendliness, but MUST NOT alter the value reported in `TerraformExecData.exit_code`, since FR-006 already establishes the two `exit_code` fields as distinct and this field's entire purpose is to be the authoritative, unmasked pass/fail/changed signal.
- Q: The same trace found `resource_counts`/`outputs`/`changes` can come back all-zero/empty even when a plan had real changes, because `terraformCaptureShellOpts` (`cmd/terraform/utils.go:855-864`) shares ONE stdout/stderr buffer across `terraform init`, `terraform workspace select`, AND the main `plan`/`apply` invocation (`internal/exec/terraform_execute_helpers_exec.go:164-220`); the shared parser (`pkg/ci/plugins/terraform.ParsePlanOutput`) short-circuits on the first occurrence of "No changes."/"Your infrastructure matches the configuration" anywhere in that combined blob (`parser.go:389-395`), discarding the real `Plan: N to add, M to change, K to destroy.` line that appears later from the actual plan phase. Should the buffer handed to the exec-metadata parser be scoped to only the final plan/apply subprocess invocation? → A: Yes — the stdout/stderr buffers fed to the exec-metadata parser MUST be reset/isolated immediately before the final `plan`/`apply` subprocess invocation, so `citerraform.ParseOutput` (via `parseTerraformOutputMirror`) only ever sees that invocation's own output, never `terraform init`'s or `terraform workspace select`'s. This is required for FR-006/SC-007's "100% of resource counts and output values visible in the plan's own output are also present in its execution record" guarantee to actually hold; the init/workspace-select phases' own output MAY still be captured separately (e.g. for logging) but MUST NOT be concatenated into the buffer the exec-metadata parser reads.
- Q: `pkg/ci/plugins/terraform.ParsePlanOutput`/`ParseApplyOutput` (used by both Native CI's own annotations and, via `parseTerraformOutputMirror`, this feature's `TerraformExecData`) are regex-over-human-readable-text parsers, structurally unable to guarantee SC-007's "100%" claim; an existing but unused `ParsePlanJSON` (`parser.go:112-135`) shows the shape for JSON-based extraction already exists but isn't wired in anywhere. Should extraction switch to terraform's `-json` streamed log format for both callers, and since `-json` suppresses terraform's normal human-readable console output, how should human-readable output still reach CI logs and the exec-metadata payload? → A: Yes — invoke terraform with `-json` for `plan`/`apply` (and `deploy`'s internal `apply`) whenever Native CI annotation processing or exec-metadata capture is active, and replace `ParsePlanOutput`/`ParseApplyOutput`'s regex extraction with a parser over the JSON message stream (extending the existing, currently-unused `ParsePlanJSON` shape rather than inventing a second JSON parser) as the single shared extraction path for both callers — this rewires `pkg/ci/plugins/terraform`, not just this feature's own code, so Native CI's annotations gain the same accuracy guarantee. Because `-json` suppresses terraform's normal human-readable console output, System MUST add a renderer that converts the parsed JSON message stream back into human-readable text equivalent to terraform's native output, and that rendered text — not raw JSON — MUST be what is (a) written to the CI console/log group in place of terraform's native output, and (b) used for any human-readable log/diagnostic text included in the exec-metadata payload (e.g. `TerraformExecData`'s `warnings`/`errors` blocks), so CI log readability and the payload's human-readable fields are unaffected by the extraction source moving to JSON.
- Q: **Correction, decided immediately after the above** — the `-json`-stream rewrite (FR-006g/FR-006h) touches the shared `pkg/ci/plugins/terraform` parser Native CI also depends on, is a materially larger and riskier change than the two concrete bugs it was bundled with, and was not actually requested — extraction should keep using the same regex-based approach Native CI already uses today. Should FR-006g/FR-006h stand, or be retracted in favor of keeping `ParsePlanOutput`/`ParseApplyOutput` (regex over human-readable text) as the extraction mechanism, fixing only the exit_code (FR-006e) and buffer-scoping (FR-006f) bugs? → A: Retracted. `FR-006g` and `FR-006h` are removed. Extraction continues via the existing `citerraform.ParseOutput`/`ParsePlanOutput`/`ParseApplyOutput` regex-over-human-readable-text parser — identical to what Native CI already does today — with no `-json` invocation, no new JSON-stream parser, and no human-readable renderer. Only FR-006e (pre-remap `exit_code` capture, unconditional `-detailed-exitcode`) and FR-006f (buffer scoped to the final subprocess invocation) remain in scope; FR-006f's buffer-scoping fix, on its own, still resolves the reported all-zero `resource_counts` symptom, since the regex parser working correctly was never the problem — parsing the wrong (combined multi-phase) text was.
- Q: FR-006e adds `-detailed-exitcode` unconditionally whenever exec-metadata capture's CI-detection gate (FR-001) is true, but `-detailed-exitcode` makes the terraform/tofu subprocess exit non-zero (2) when a plan has changes — a behavior Atmos's own process exit code does not have today without it. If the CI-mode exit-code remap (which neutralizes exit 2 back to a CI-friendly value) is gated by a separate condition (`ci.enabled`/`--ci`/`ATMOS_CI`) that doesn't always coincide with FR-001's CI-detection gate, could this fix silently change Atmos's own process exit code for `plan`/`apply`/`deploy` in some CI environments? → A: Yes, this is a real risk that MUST be closed. Whenever exec-metadata capture's CI-detection gate (FR-001) is true for a `plan`/`apply`/`deploy` invocation, the CI-mode exit-code remap MUST also be treated as active for that same invocation, so the terraform/tofu subprocess's `-detailed-exitcode`-induced exit 2 is always neutralized before it becomes Atmos's own process exit code. Atmos's own process exit code for `plan`/`apply`/`deploy` MUST be unaffected by FR-006e's addition of `-detailed-exitcode` — this is a guarantee, not merely an expectation contingent on a separately-configured `ci.enabled`/`--ci` flag also happening to be set.
- Q: `-detailed-exitcode` was added to `terraform apply`/`destroy` starting in Terraform 1.5+ (OpenTofu supports it too), but Atmos supports arbitrary pinned terraform/tofu binary versions via `atmos.yaml`; an older pinned binary would hard-fail on an unrecognized flag if `-detailed-exitcode` were added to `apply`/`deploy`'s internal `apply` invocation unconditionally. Should FR-006e's `-detailed-exitcode` addition be scoped to `plan` only (universally supported since early Terraform versions), dropping it from `apply`/`deploy`? → A: Yes — `-detailed-exitcode` is added to `plan` only. `apply`/`deploy`'s internal `apply` invocation does NOT receive `-detailed-exitcode` and keeps its current plain 0 (success) / 1 (error) exit-code semantics; no version-detection/fallback logic is needed since the flag is never added to `apply` in the first place. `TerraformExecData.exit_code` for `apply`/`deploy` continues to be captured pre-CI-remap (FR-006e's other guarantee still applies to all three subcommands, since CI-mode remap could in principle affect any exit code, not just detailed-exitcode's 2), but its value space for `apply`/`deploy` remains 0/1, not the 0/1/2 detailed range `plan` now reliably produces. `has_changes`/`has_errors` for `apply`/`deploy` continue to come from parsing the subprocess's own output (e.g. "Apply complete! Resources: N added..."), not from exit-code value, consistent with `apply`'s exit code never having signaled "changed vs. unchanged" even before this feature.

### Session 2026-08-20

- Q: For terraform plan/apply/deploy output values in the structured Data payload (FR-006), should outputs that Terraform itself marks sensitive (e.g. `sensitive = true` in the output block) be masked independently of Atmos's existing gitleaks-pattern secret masking (FR-010)? → A: Both, applied independently — a Terraform-sensitive-flagged output is masked with a fixed placeholder as a dedicated rule, and the existing gitleaks-pattern scanning (FR-010) still runs over the remaining, non-sensitive-flagged output values as a separate layer.
- Q: FR-006 already requires warnings/errors in the structured Data payload, but the structured-data shape as implemented only carries `warnings` — no `errors`, `has_changes`, or `has_errors` fields. Should the structured Data shape be extended to add `has_changes`, `has_errors`, and `errors` alongside the existing `resource_counts`/`outputs`/`warnings`/`changes`? → A: Yes — add `has_changes`, `has_errors`, and `errors` as top-level fields of the structured Data payload, sourced from the same per-run parse result that already produces `resource_counts`/`outputs`/`warnings`, giving Atmos Pro a direct pass/fail/changed signal without inferring it from `changes`/`warnings`.
- Q: For a single-component `terraform plan`/`apply`/`deploy` invocation, should the structured Data payload also carry the invocation's own `component`/`stack` identity as dedicated fields, rather than leaving Atmos Pro to infer them from the base envelope's `args`/`flags`? → A: Yes — add `component` and `stack` as top-level fields of the structured Data payload for `terraform plan`/`apply`/`deploy`, populated from the same invocation identity already available to the command (`info.Component`/`info.Stack`), giving Atmos Pro first-class identity fields instead of requiring it to parse `args[0]`/the `--stack` value out of `flags`.
- Q: `describe affected` is on the synchronous allowlist (FR-007) but has no structured Data defined at all (FR-006 only covers `terraform plan`/`apply`/`deploy`) — it should carry the same per-stack data already uploaded to `POST /api/v1/affected-stacks` (`UploadAffectedStacksRequest.Stacks []schema.Affected`). What should the wire shape be? → A: `Data` is a JSON object with one key, `stacks`, holding the array of `schema.Affected` entries verbatim (component, component_type, stack, affected reason, dependents, settings, etc.) — matches every other command's `Data` being an object, not a bare array. Fields already present in the base envelope (`repo_url`/`repo_name`/`repo_owner`/`repo_host`, `git_sha`) are NOT duplicated from `UploadAffectedStacksRequest`'s `HeadSHA`/`BaseSHA`/repo fields.
- Q: `atmos list instances`'s existing `--upload` flag gates whether it computes the `[]UploadInstance` list and calls `POST /api/v1/instances` at all. Should the new exec-metadata `Data` payload for `list instances` only be populated when `--upload` was passed (reusing the already-computed list), or should it always compute and attach the instance list regardless of `--upload`? → A: Only when `--upload` is passed — `Data` mirrors exactly what `--upload` already computed and sent to `POST /api/v1/instances` (a `{"instances": [...]}` object, same wrapped-object convention as `describe affected`'s `{"stacks": [...]}`, excluding the base-envelope-duplicate `repo_url`/`repo_name`/`repo_owner`/`repo_host` fields). Without `--upload`, `list instances`' execution record has no structured `Data`, same as any other command with nothing to attach (FR-005) — no extra computation cost is added to the plain (non-uploading) invocation.
- Q: Which structs should get a new `version` field for Atmos Pro server-side struct validation/parsing — only the command-specific `Data` payload shapes, or also the outer envelope structs (`ExecUploadRequest`/`ExecDataUploadRequest`)? → A: Only the command-specific `Data` shapes (`TerraformExecData`, `describe affected`'s `{stacks}`, `list instances`' `{instances}`) — each gets its own top-level `version` field inside its `Data` object, versioned independently of the comparatively stable outer envelope, which is not versioned by this change.
- Q: What should the `version` field's value be? → A: A plain incrementing integer per shape, starting at `1` — bumped only when that specific shape's own fields change in a way the Pro server needs to branch on; not tied to the Atmos release version, and not a semver string.
- Q: For each command's structured Data shape (`TerraformExecData`, `describe affected`'s `{stacks}`, `list instances`' `{instances}`), the Pact contract test suite needs cases exercising both the inline and blob-URL delivery modes. Since a genuinely-large (>4 MB) fixture is unwieldy in a Pact consumer test, how should the blob-URL case be produced? → A: Construct both request shapes directly and independently — one Pact interaction with `Data` inline, a separate one with `Data` as a URL string returned by a preceding `POST /v1/atmos/exec/data` interaction — without routing either through the real size-threshold decision code. The threshold-check logic itself (inline vs. blob-URL selection) continues to be verified by separate, non-Pact unit tests, not by the Pact suite.
- Q: FR-006b (`describe affected` structured data) and FR-006c (`list instances` structured data) don't fit User Story 3's stated scope (`terraform plan`/`apply`/`deploy` only) — how should the spec resolve the gap? → A: Add a new User Story, US4 ("Pro inventory visibility for `describe affected` and `list instances`", Priority P4), with its own goal, independent test, and acceptance scenarios, so FR-006b/FR-006c have the same traceable user-facing story and independent-test coverage as every other structured-data requirement.
- Q: A real CI payload (`atmos-pro-qa-3` run 32412509172) showed `errors: null` and `changes: null` for a run with none of either, even though data-model.md's own worked example shows `"errors": []` for the empty case — a nil-Go-slice-marshals-to-`null` artifact. Should FR-006's structured Data require all list-typed fields to always serialize as `[]`, never `null`, when empty? → A: Yes — every list-typed field in every command-specific structured `Data` shape defined by this feature (`TerraformExecData`'s `changes`/`warnings`/`errors`, and any future shape's list fields) MUST serialize as `[]` when empty, never `null`; this is a wire-shape guarantee, not merely a documentation example.
- Q: The same real payload showed `has_changes: true` alongside all-zero `resource_counts` and an empty `outputs` object — the top-level status flags and the itemized data can silently disagree when the terraform-output parser detects a change but fails to extract itemized details. Should the spec define required behavior for this divergence (e.g. a new partial-parse indicator)? → A: No new indicator — instead, `TerraformExecData` gains a new top-level `exit_code` field: the terraform/tofu subprocess's own process exit code (distinct from the base envelope's `exit_code`, which is atmos's own process exit code and may differ, especially for multi-component `--affected`/`--all` runs). Consumers MUST treat `exit_code` — not the presence/absence of itemized `resource_counts`/`outputs`/`changes` — as the authoritative signal for whether a plan/apply/deploy actually failed or was fully parsed; empty/zero itemized fields next to `has_changes: true` remain a valid, unflagged state precisely because `exit_code` is now available to disambiguate it.
- Q: For a multi-component `--affected`/`--all` run (FR-006a folds each component's structured data into one aggregate record), where does the new `exit_code` field live — one aggregate top-level value, or per-component? → A: Per-component only — each component's entry in the folded breakdown carries its own `exit_code` (each component runs its own terraform/tofu subprocess with its own exit code); there is no separate top-level aggregate `exit_code`, since FR-006's `exit_code` is explicitly scoped to "the terraform/tofu subprocess," and a multi-component run has N subprocesses, not one.
- Q: Today, a totally-unparseable terraform output (e.g. the subprocess crashed with no recognizable terraform output at all) causes `buildTerraformExecData` to return no `Data` whatsoever. ## User Scenarios & Testing *(mandatory)*

### User Story 1 - Automatic visibility into CI command execution (Priority: P1)

As an organization running Atmos in CI with Atmos Pro configured, I want every `atmos` command invocation to automatically report its execution outcome (what ran, exit code, environment, resource consumption) to Atmos Pro, so that our team has a complete, automatic audit trail of infrastructure operations without any extra CI configuration.

**Why this priority**: This is the foundational capability — without it, no execution data reaches Atmos Pro at all. It delivers value the moment it ships: visibility into CI activity that previously required manually parsing CI logs.

**Independent Test**: Run any `atmos` command (e.g. `atmos version`, `atmos describe stacks`) in a CI environment with Atmos Pro configured, and confirm a corresponding execution record appears on the Atmos Pro side with correct version, command, exit code, and resource-usage fields. Can be fully tested without any per-command structured data or synchronous delivery.

**Acceptance Scenarios**:

1. **Given** Atmos is running inside a recognized CI provider and Atmos Pro is configured with valid credentials, **When** any `atmos` command completes (success or failure), **Then** an execution record containing the command's identity, exit code, environment info, and resource-usage metrics is sent to Atmos Pro.
2. **Given** Atmos is running on a developer's local machine (not CI), **When** any `atmos` command completes, **Then** no execution record is sent to Atmos Pro.
3. **Given** Atmos is running in CI but Atmos Pro is not configured, **When** any `atmos` command completes, **Then** no execution record is sent to Atmos Pro.
4. **Given** Atmos Pro is unreachable or returns an error, **When** a command whose upload is fire-and-forget completes, **Then** the command's own exit code and output are unaffected by the delivery failure.

**Why this priority**: Builds directly on User Story 1's delivery mechanism; only meaningful once basic reporting exists. It matters most for the highest-stakes commands, which is why it is scoped to a small, well-defined set rather than all commands.

### Edge Cases

- What happens when the CI environment is detected but Atmos Pro authentication has expired or is rejected (401)? The existing Atmos Pro client's token-refresh/retry behavior applies; if it still cannot authenticate, the upload is treated as a failed delivery per that command's configured behavior (fail vs. warn-and-continue).
- What happens on an operating system where fine-grained resource metrics (e.g. peak memory, page faults) are unavailable (e.g. Windows)? The execution record is still sent with the fields that are available (e.g. wall time), and unavailable fields are omitted rather than blocking delivery.
- What happens when the additional structured JSON data for a command is very large (e.g. a plan touching thousands of resources)? If the total record (base envelope + resource-usage metrics + `Data`) would be at or above 4 MB, `Data` is uploaded once to `POST /v1/atmos/exec/data` (tagged with `ExecutionID`/`execution_id`), and the returned blob URL is sent in `Data`'s place on the main `POST /v1/atmos/exec` request; the base envelope and resource-usage metrics are always sent in full. The complete data set is delivered without truncation or loss, in exactly one additional request, never split across multiple chunk requests.
- What happens if a command's arguments or structured data would otherwise contain secret values? Consistent with Atmos's existing secret-masking behavior, sensitive values must never be included in the uploaded payload.
- What happens when a command is interrupted (e.g. Ctrl-C) mid-execution? Best-effort delivery of a partial/aborted execution record is acceptable; a synchronous command being interrupted must not hang indefinitely waiting on delivery.
- What happens when the same CI job runs many `atmos` commands in sequence (e.g. a workflow)? Each command execution produces its own independent execution record.
- What happens when a single `atmos terraform plan`/`apply` CLI invocation targets multiple components in one run (`--affected`/`--all`)? The invocation still produces exactly one execution record overall, not one per component; each component's identity, outcome, and any structured data (FR-006) are folded into that single record's command-specific structured-data field.
- What happens when both this feature's execution-record upload and the pre-existing `uploadStatus`/`--upload-status` PATCH mechanism (a separate, independently-gated upload path used for lightweight instance-status tracking) fire for the same `terraform plan`/`apply` invocation? Both proceed independently — the Atmos client does not merge, skip, or coordinate between them, and any cross-record correlation or deduplication of the two resulting records is the Atmos Pro backend's responsibility. The one client-side guarantee is that this feature's execution record reports its `Command` as the bare subcommand path (e.g. `"terraform plan"`), its `Args` as the invocation's positional arguments (e.g. the component), and its `Flags` as the CLI flags actually passed (FR-003b), keeping it correlatable in content with `uploadStatus`'s `Command`/`Component`/`Stack` fields for that same invocation, even without a shared record ID.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST determine whether the current invocation qualifies for execution-metadata upload by checking that both (a) Atmos is running inside a recognized CI environment, and (b) Atmos Pro is configured with usable credentials.
- **FR-002**: System MUST NOT send any execution metadata when either condition in FR-001 is not met, and this behavior MUST require no additional user configuration beyond the existing CI and Atmos Pro setup.
- **FR-003**: For every qualifying command execution, system MUST report a base execution record containing: Atmos version, operating system, architecture, the full command invoked, any command-specific additional arguments, the command's exit code, source-control identification (e.g. commit/repository info), and the existing Atmos Pro run identifier, consistent with what other Atmos Pro uploads already capture.
- **FR-003c**: System MUST generate a fresh `ExecutionID` (a UUID v4) once per qualifying command invocation and include it in the base execution record, distinct from and in addition to the existing Atmos Pro run identifier (FR-003): the run identifier correlates records across a CI run, while `ExecutionID` uniquely identifies this single execution record. When `Data` must be uploaded out-of-band (FR-011), `ExecutionID` MUST also be sent as the `execution_id` field on that upload, so Atmos Pro can associate the stored blob with this execution record.
- **FR-003a**: This feature's execution-record upload (`POST /v1/atmos/exec`) and the pre-existing `uploadStatus`/`--upload-status` PATCH mechanism (`internal/exec/pro.go`) are separate, independently-gated upload paths. System MUST NOT merge them, skip either one because the other fired, or otherwise make them mutually exclusive; any cross-record correlation or deduplication between the two record types on the Atmos Pro side is out of scope for this feature.
- **FR-003b**: The execution record's `Command` field MUST be the subcommand path without the leading `atmos` root segment (e.g. `"terraform plan"`, not `"atmos terraform plan"`). The `Args` field MUST hold only the invocation's positional arguments (e.g. the component identifier: `["cdn"]`); it MUST NOT be left empty for an invocation that received positional arguments. A separate `Flags` field MUST hold every CLI flag actually passed by the user, with no exclusions — including `--upload-status` and any other flag Atmos itself consumes internally — using each flag's canonical long name (e.g. `--stack`, even if the user typed the shorthand `-s`), e.g. `["--stack", "plat-use2-dev", "--upload-status"]`; a boolean/valueless flag like `--upload-status` MUST appear alone with no synthesized value appended (a value-bearing flag like `--stack` still contributes both its token and its value as separate array entries). Array order reflects the CLI framework's own flag-iteration order and is NOT required to match the order flags were typed on the command line (2026-08-19 clarification — literal shorthand/order preservation was considered and explicitly rejected as unnecessary, since it would require parsing raw pre-parse command-line tokens instead of the framework's already-parsed flag set). `Flags` MUST NOT be derived from a leftover/pass-through-args collection that never captured atmos-recognized flags in the first place (it MUST be sourced from the invoking command's own record of explicitly-set flags), and MUST NOT be left empty for an invocation that received flags. Positional args and flags MUST be kept in distinct fields, not combined into one array. This shape keeps `Command`/`Args`/`Flags` correlatable in practice with `uploadStatus`'s bare-subcommand `Command` and its separate `Component`/`Stack` fields for the same invocation, even though the two upload paths remain fully independent per FR-003a.
- **FR-004**: System MUST report resource-usage metrics for the command's execution, including at minimum wall-clock duration and CPU time, with additional metrics (peak memory, page faults, context switches, block I/O) included whenever the host platform makes them available.
- **FR-005**: System MUST support commands attaching additional, command-specific structured data to their execution record; commands that do not define such data MUST still have their base execution record and resource-usage metrics sent normally.
- **FR-005a**: Every command-specific structured `Data` shape defined by this feature (FR-006's `TerraformExecData`, FR-006b's `describe affected` shape, FR-006c's `list instances` shape, and any future shape) MUST include a top-level `version` field: a plain integer, starting at `1`, identifying that specific shape's own schema version — independent of the Atmos release version and independent of every other shape's `version`. System MUST increment a given shape's `version` only when that shape's own fields change in a way the receiving Atmos Pro server needs to branch on, so the server can validate/parse each command's structured data according to its declared shape version. The outer envelope (`ExecUploadRequest`/`ExecDataUploadRequest`) is not versioned by this requirement.
- **FR-006**: System MUST attach structured infrastructure-change data (created/updated/deleted/replaced resources, output values, warnings/errors) to the execution record for `terraform plan`, `terraform apply`, and `terraform deploy` (`deploy`'s structured data uses the identical `TerraformExecData` shape — `deploy` runs as a single `terraform apply -auto-approve` subprocess internally, not two separate subprocesses, so there is no plan/apply sub-object split for it, per the correction above). This structured data MUST include top-level `has_changes` and `has_errors` boolean flags and an `errors` list, alongside the existing itemized resource changes and `warnings` list, so a consumer can determine the run's pass/fail/changed status without inferring it from the itemized data. This structured data MUST also include an `exit_code` field — the terraform/tofu subprocess's own process exit code, distinct from the base execution record's own `exit_code` (FR-003) — as the authoritative pass/fail signal a consumer relies on instead of inferring failure or incomplete parsing from empty/zero itemized fields (`resource_counts`/`outputs`/`changes`). For a single-component invocation, `exit_code` is a top-level field alongside `component`/`stack`; for a multi-component `--affected`/`--all` invocation (FR-006a), `exit_code` is instead reported per-component on each entry in the folded breakdown, never as a single aggregate top-level value, since each component runs its own terraform/tofu subprocess with its own exit code. Every list-typed field in this structured data (`changes`, `warnings`, `errors`) MUST serialize as `[]`, never `null`, when empty. When a component's terraform output cannot be parsed at all (e.g. the subprocess produced no recognizable terraform output), System MUST still attach `TerraformExecData` for that component with `version`, `exit_code`, and `component`/`stack` (when known) populated and every unparseable field defaulted (`resource_counts` all zero, `outputs: {}`, `changes`/`warnings`/`errors`: `[]`, `has_changes`/`has_errors`: `false`) rather than omitting structured data entirely — `exit_code` MUST remain available precisely in the case it is needed most. For a single-component invocation, the structured data MUST also include top-level `component` and `stack` fields identifying the invocation's target, so a consumer does not need to infer them from the base envelope's `Args`/`Flags`. Per FR-005a, this structured data MUST also include a top-level `version` field.
- **FR-006a**: When a single `terraform plan`/`apply` CLI invocation targets multiple components in one run (e.g. `--affected`/`--all`), System MUST report exactly one execution record for the whole invocation, not one per component; each component's identity, outcome, and structured data (FR-006) MUST be folded into that single record's command-specific structured-data field rather than sent as separate, independent execution records.
- **FR-006e**: System MUST add `-detailed-exitcode` to every `plan` invocation whenever exec-metadata capture is active, independent of and not gated behind the pre-existing `--upload-status` flag. `apply`/`deploy`'s internal `apply` invocation does NOT receive `-detailed-exitcode` (dropped from scope: an older pinned terraform/tofu binary may not support it on `apply`, and `apply`'s exit code never signaled "changed vs. unchanged" even before this feature) and keeps its current plain 0 (success) / 1 (error) exit-code semantics. `TerraformExecData.exit_code` (FR-006), for all of `plan`/`apply`/`deploy`, MUST be the terraform/tofu subprocess's real, pre-CI-remap exit code, captured before CI-mode's exit-code remapping (which may still determine Atmos's own process exit code, i.e. the base envelope's `exit_code` per FR-003, for CI-friendliness) is applied. CI-mode remapping MUST NOT alter the value reported in `TerraformExecData.exit_code`. Whenever exec-metadata capture's CI-detection gate (FR-001) is true for the invocation, the CI-mode exit-code remap MUST also be treated as active for that same invocation, so `plan`'s `-detailed-exitcode`-induced exit-2 ("changes detected") is always neutralized before it becomes Atmos's own process exit code — adding `-detailed-exitcode` per this requirement MUST NOT change Atmos's own process exit code for `plan` in any CI environment satisfying FR-001, regardless of whether `ci.enabled`/`--ci`/`ATMOS_CI` was separately/explicitly set.
- **FR-006f**: The stdout/stderr text System parses to populate `TerraformExecData`'s `resource_counts`/`outputs`/`changes`/`warnings`/`errors`/`has_changes`/`has_errors` (FR-006) MUST be scoped to only the final `plan`/`apply` (or `deploy`'s internal `apply`) subprocess invocation for that component. System MUST NOT concatenate `terraform init`'s or `terraform workspace select`'s output into that same buffer before parsing, since either phase's incidental output (e.g. a stray "No changes."-shaped message) can cause the shared parser to short-circuit and silently under-report a plan/apply that had real changes.
- **FR-006g, FR-006h**: Retracted (2026-08-21 correction, see Clarifications). Extraction remains regex-based via the existing `ParsePlanOutput`/`ParseApplyOutput` — the same mechanism Native CI already uses — not a `-json`-stream parser; no human-readable-renderer requirement applies.
- **FR-006b**: System MUST attach structured data to the execution record for `describe affected`, reusing the same per-stack data already reported to the existing `POST /api/v1/affected-stacks` upload (one entry per affected component/stack, including its identity, the reason it is affected, its dependents, and its settings). This structured data MUST be a JSON object with a `stacks` key holding that array, plus (per FR-005a) a top-level `version` field; fields already present in the execution record's base envelope (repository URL/name/owner/host, git SHA) MUST NOT be duplicated inside this structured data.
- **FR-006c**: System MUST attach structured data to the execution record for `atmos list instances` only when its existing `--upload` flag was passed for that invocation, reusing the same instance list already reported to the existing `POST /api/v1/instances` upload (one entry per instance, including its component, stack, component type, and settings). This structured data MUST be a JSON object with an `instances` key holding that array, plus (per FR-005a) a top-level `version` field; fields already present in the execution record's base envelope (repository URL/name/owner/host) MUST NOT be duplicated inside this structured data. When `--upload` was not passed, `list instances`' execution record MUST have no structured data, consistent with FR-005, and System MUST NOT compute the instance list solely to populate this field.
- **FR-007**: System MUST treat `terraform plan`, `terraform apply`, `terraform deploy`, and `describe affected` as commands whose execution-record delivery blocks command completion (synchronous), and MUST treat all other commands as fire-and-forget (asynchronous), matching each command's fixed, code-defined classification. These two delivery paths are mutually exclusive per invocation: a command on the synchronous allowlist MUST NOT also receive an asynchronous default-path upload for the same invocation — every qualifying command execution produces exactly one execution record, never two.
- **FR-008**: For each command classified as synchronous, the command's own implementation MUST define whether a delivery failure causes the command itself to fail, or is treated as a non-fatal warning that still allows the command to complete; system MUST guarantee one of these two outcomes occurs (never a silent, indefinite hang).
- **FR-008a**: System MUST bound how long a synchronous command waits for its complete execution-record upload (including the `POST /v1/atmos/exec/data` blob upload, if `Data` required out-of-band delivery per FR-011) to be confirmed, defaulting to approximately 10 seconds total, and this wait duration MUST be configurable by the user to a longer value.
- **FR-009**: For commands classified as asynchronous, a delivery failure MUST NOT alter the command's own exit code or block its completion. The process MUST perform a short, bounded best-effort wait to maximize the chance the upload is dispatched before exiting, rather than exiting with no delivery guarantee at all.
- **FR-009a**: An asynchronous upload failure MUST be silent to the user by default (no warning/error printed), surfaced only at debug/verbose log level, consistent with existing telemetry failure handling.
- **FR-010**: System MUST exclude or mask any secret/sensitive values from command arguments and structured data before inclusion in an execution record, consistent with Atmos's existing secret-masking behavior.
- **FR-010a**: For `terraform plan`/`apply`/`deploy` output values included in the structured Data payload (FR-006), System MUST apply two independent masking layers: (1) any output that Terraform itself marks sensitive (`sensitive: true` in the plan/state JSON) MUST be replaced with a fixed placeholder value before inclusion, regardless of whether its content would also match a secret pattern; and (2) the existing gitleaks-pattern secret masking (FR-010) MUST still be applied to the remaining, non-sensitive-flagged output values. Layer (1) MUST NOT be skipped on the assumption that layer (2) would catch the same value, since a Terraform-sensitive-flagged value (e.g. an internal ID) may not match any known secret pattern.
- **FR-011**: System MUST NOT truncate or drop command-specific structured data due to payload size. Before sending an execution record, System MUST estimate the total marshaled size of the whole record (base envelope + resource-usage metrics + `Data` combined) and compare it against a fixed 4 MB threshold (not user-configurable):
  - If the total size is below 4 MB, `Data` MUST be included inline, as a JSON structure, directly in the `POST /v1/atmos/exec` request.
  - If the total size is at or above 4 MB, System MUST first upload `Data`'s JSON structure in a single request to `POST /v1/atmos/exec/data`, tagged with the record's `ExecutionID` via an `execution_id` field (FR-003c). On success, Atmos Pro returns a URL identifying the stored blob; System MUST then set the main record's `Data` field to that URL string (in place of the inline structure) before sending the record to `POST /v1/atmos/exec`.
  `Data` is therefore always exactly one of two shapes on the wire — an inline JSON structure, or a string URL — never both, and the `POST /v1/atmos/exec/data` upload is always exactly one request regardless of size (no client-side chunking; the blob store handles arbitrarily large uploads in a single call). This fully replaces the previous multi-chunk/batch-correlation model — there is no longer any splitting of a single field across multiple correlated requests anywhere in this feature. The base envelope and resource-usage metrics are never affected by this and are always sent in full as part of whichever `POST /v1/atmos/exec` request carries them.
- **FR-011a**: The `POST /v1/atmos/exec/data` upload, when required, MUST count toward the same delivery-timing budget as the main `POST /v1/atmos/exec` call for that execution record: for synchronous commands, both requests together MUST complete within the existing ~10 second total ceiling (FR-008a); for asynchronous commands, both requests together MUST fit within the existing short bounded best-effort flush window (FR-009) — if the sequence cannot complete in time, the record is dropped silently per FR-009a, same as any other async delivery failure.
- **FR-012**: System MUST authenticate execution-record uploads using the same credential/token mechanism already used for other Atmos Pro API calls, including automatic token refresh on expiry.
- **FR-013**: A verifiable, versioned description of the exact request and response shape for the execution-metadata upload MUST exist and be kept up to date as the payload evolves, in a form that the Atmos Pro team can use to implement and validate the receiving endpoint independently of the Atmos codebase.

### Key Entities

- **Execution Record**: Represents a single `atmos` command invocation's reported outcome — exactly one record per CLI invocation, including a multi-component `--affected`/`--all` run (FR-006a), never one record per component. Includes identity (bare subcommand path, positional arguments, CLI flags, exit code — FR-003b), a fresh per-invocation `ExecutionID` (UUID v4 — FR-003c) that uniquely identifies this record and, when `Data` requires out-of-band delivery, keys the correlated `POST /v1/atmos/exec/data` upload (FR-011), environment (Atmos version, OS, architecture), source-control context, resource-usage metrics, an optional command-specific structured-data payload (which, for a multi-component invocation, itself contains the per-component breakdown, and is either inline JSON or a blob URL per FR-011), and the existing Atmos Pro run identifier already used by other Pro uploads, for correlation across a CI run and deduplication of retried uploads.
- **Resource Usage Metrics**: Represents how much time and system resources a command consumed while running — wall-clock duration, CPU time, and (where available) peak memory, page faults, context switches, and block I/O.
- **Command Structured Data (`Data`)**: Represents optional, command-specific enrichment attached to an Execution Record. Every shape carries its own top-level `version` field (a plain integer starting at `1`, incremented independently per shape — FR-005a) so Atmos Pro can validate/parse each command's structured data against its declared shape version. For `terraform plan`/`apply`/`deploy`, this is the set of created/updated/deleted/replaced resources, output values, warnings/errors (list-typed fields always `[]`, never `null`, when empty), top-level `has_changes`/`has_errors` status flags, the terraform/tofu subprocess's own `exit_code` (the authoritative pass/fail/parse-completeness signal, distinct from the base envelope's own `exit_code` — reported per-component in a multi-component `--affected`/`--all` run, never as one aggregate value, and always populated even when itemized parsing fails entirely), and (for a single-component invocation) the invocation's own `component`/`stack` identity, produced by that run. `terraform deploy` uses this identical shape, not a split view — `deploy` runs as a single `terraform apply -auto-approve` subprocess internally (`internal/exec/terraform.go`'s `handleDeploySubcommand` rewrites `deploy` to `apply` before any subprocess runs), so there is no separate plan-phase output/exit-code to report (corrected during implementation from an earlier, factually-wrong two-phase design). For `describe affected` (FR-006b), this is a `{"version": 1, "stacks": [...]}` object holding the same per-stack entries (identity, affected reason, dependents, settings) already reported to the existing `POST /api/v1/affected-stacks` upload, reusing that data rather than defining a second, divergent shape. For `atmos list instances` (FR-006c), this is a `{"version": 1, "instances": [...]}` object holding the same per-instance entries already reported to the existing `POST /api/v1/instances` upload, present only when the invocation passed `--upload` (otherwise structured data is simply absent, per FR-005). Output values pass through two independent masking layers before inclusion (FR-010a): Terraform-sensitive-flagged outputs are replaced with a fixed placeholder, and the remaining outputs still pass through the existing gitleaks-pattern secret masking (FR-010). On the wire it is always exactly one of two shapes: an inline JSON structure (when the whole record is under 4 MB), or a string URL to a blob uploaded via `POST /v1/atmos/exec/data` and keyed by `ExecutionID` (when the whole record is at or above 4 MB) — never truncated or dropped, and never split across multiple requests. The base envelope and resource-usage metrics are unaffected and always delivered in full.
- **Execution Contract**: Represents the agreed, verifiable shape of the data exchanged between Atmos and Atmos Pro for execution-metadata upload, independent of either side's internal implementation.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of `atmos` command executions that run in a recognized CI environment with Atmos Pro configured produce a corresponding execution record on the Atmos Pro side, with no additional setup beyond existing CI/Pro configuration.
- **SC-002**: 0% of command executions outside CI, or in CI without Atmos Pro configured, produce any outbound execution-metadata traffic.
- **SC-003**: For `terraform plan`, `terraform apply`, `terraform deploy`, and `describe affected`, 100% of runs either confirm successful delivery of their complete execution record — including the `POST /v1/atmos/exec/data` blob upload, if `Data` required out-of-band delivery (FR-011) — within the configured total wait period (~10 seconds by default), or exit through one of the two explicitly defined failure paths (fail command / warn and continue) — never an indefinite wait.
- **SC-004**: For all other commands, execution-metadata delivery adds no more than a brief, bounded delay to command completion as perceived by the user (fire-and-forget with a short best-effort flush, not a blocking wait for confirmation).
- **SC-005**: An outage or error response from Atmos Pro causes zero unexpected exit-code changes for asynchronous commands, and causes only the explicitly configured behavior (fail or warn) for synchronous commands.
- **SC-006**: A reviewer on the Atmos Pro team can determine the exact request/response shape for execution-metadata upload from a single, versioned artifact, without reading Atmos's Go source code.
- **SC-007**: For a `terraform plan` run with pending changes, 100% of the created/updated/deleted/replaced resource counts and output values visible in the plan's own output are also present in its execution record — the existing regex-based parser (same as Native CI's) reads only that run's own subprocess output, scoped per FR-006f, so it is no longer polluted by unrelated init/workspace-select text.

## Assumptions

- "Recognized CI environment" reuses Atmos's existing CI-detection behavior (environment-variable-based provider detection) rather than introducing a new detection mechanism.
- "Atmos Pro configured" means a usable authentication path already exists (a static token, or GitHub OIDC plus workspace identification) via Atmos's existing Atmos Pro configuration — no new configuration surface is introduced by this feature.
- The set of commands treated as synchronous (`terraform plan`, `terraform apply`, `terraform deploy`, `describe affected`) is fixed by this feature's initial implementation; commands are not user-configurable as synchronous or asynchronous.
- The mechanism by which an individual command supplies its structured data (FR-005) is an internal implementation concern and is intentionally not specified here; it must not require any user-facing configuration.
- Resource-usage metrics that are platform-specific (e.g. detailed memory/IO counters available on Unix-like systems but not Windows) are best-effort and their absence on unsupported platforms is expected, not an error.
- The "Execution Contract" (FR-013) is delivered as a consumer contract test artifact, following the same local-only, no-broker pattern already established for Atmos's other Atmos Pro API interactions. For every command that defines a structured Data shape (`terraform plan`/`apply`/`deploy`'s `TerraformExecData`, `describe affected`'s `{stacks}`, `list instances`' `{instances}`), it MUST cover both `Data`-delivery shapes for `POST /v1/atmos/exec` — inline JSON, and blob-URL reference (paired with the corresponding `POST /v1/atmos/exec/data` blob-upload interaction) — as distinct Pact interactions/cases per shape, not only for one representative command. Each pair is constructed directly (one interaction with `Data` inline, one with `Data` as a URL string) rather than by routing a fixture through the real size-threshold decision code; that threshold logic is verified separately by unit tests, not by the Pact suite.
- This feature does not define what Atmos Pro does with received execution records (storage, retention, display) — that is out of scope and owned by the Atmos Pro application. This includes any correlation or deduplication Atmos Pro may perform between this feature's execution records and records produced by the separate, pre-existing `uploadStatus`/`--upload-status` mechanism (FR-003a/FR-003b); the Atmos client's only obligation is to keep `Command`/`Args` consistent across both paths.
- No new user-facing opt-out flag is introduced; the feature is active whenever the CI + Pro-configured condition (FR-001) is met. The single new user-facing setting is the synchronous-upload wait timeout (FR-008a), which only lengthens the default wait and cannot be used to disable delivery.
