# Import deployments from Atlantis

**Status** — Proposed inbound import. Atmos already [generates Atlantis configuration](../../../website/docs/cli/commands/atlantis/atlantis-generate-repo-config.mdx). Uses the [shared CLI contract](README.md) and the [Terraform](terraform.md) and [Terragrunt](terragrunt.md) adapters.

## Outcome

A team can reproduce one existing project's plan locally while continuing to use its current Atlantis PR workflow. Importing a deployment does not establish parity with every CI stage. Report project discovery, local planning, and CI execution separately.

```shell
atmos stack add ./atlantis.yaml --dry-run
atmos stack add ./atlantis.yaml --project network-dev -s dev
atmos terraform plan network -s dev
```

When path-based plan finds applicable Atlantis projects, use them as candidates. For two projects sharing a root, offer their existing names, workspaces and ordered var-file paths in one picker. A selection supplies all values documented by that project.

## What can ship first

Ship a read-only inventory of explicit v3 projects before offering conversion. A named project with a literal directory, effective workspace and known plan workflow can then delegate to the corresponding Terraform or Terragrunt adapter. Every required input must pass that adapter’s save criteria. A useful first result for a custom workflow is a precise explanation of the first unresolved step and which other projects can already be planned.

| Example evidence | What the user sees | What can be saved initially |
| --- | --- | --- |
| Literal directory and an effective built-in `init` and `plan` | Project, directory, distribution/version, workspace and source of effective defaults. | Runnable local plan once backend, credentials context and tool selection are accounted for. Approval and locking remain visible as Atlantis settings. |
| Named workflow with a built-in plan step whose `extra_args` contain two literal var files | Both paths in order, resolved from the project working directory. | Runnable after ordered-file parity in the underlying adapter. A file listed only in `when_modified` supplies no plan argument. |
| `run: ./prepare.sh` before plan, computed `env` or missing server workflow | Exact project, workflow, stage, step and missing effect, such as a generated backend. | Inventory preview only for this project. In a TTY offer a different project or supplied effective configuration. A yes/no confirmation cannot resolve a script’s effects. |
| Reproducible plan and custom apply consuming `$PLANFILE` | Local plan available. Atlantis owns reviewed-plan storage, apply and approval. | A local planning entry only if the preview makes the remaining CI boundary explicit. Avoid representing this as an equivalent deployment pipeline. |
| Globbed `dir`, implicit autodiscovery or projects generated by a server hook | Explicit declarations, unresolved inventory scope and required expansion context. | Defer expanded import until upstream project enumeration matches the same checkout and server settings. An empty explicit list can still have undiscovered projects. |

For the initial workflow translator, allow built-in init and plan with a tested set of literal arguments. Treat shell-form `run` as unresolved. Recognizing a small set of exact commands, tracking environment across steps, translating dependencies, and moving policy or PR automation are separate milestones. A normal Atmos Terraform component exposes other Terraform operations too. Printing “plan available” cannot enforce Atlantis gates. If the product needs a plan-only execution restriction, require a tested enforcement mechanism before publishing those components into a bulk-apply stack. Users can keep working in inventory-only mode in the meantime. [Upstream custom workflows](https://www.runatlantis.io/docs/custom-workflows.html)

**Round-trip evidence.** Generating configuration from the checked-in demo produced `projects: []` and a declared `workflow-1`. Its stack manifest is empty and its project template does not bind that workflow. Adding a sample component produced a project with workspace `default` and no workflow binding. Its generated project also omitted the intended apply approval, which the template places inside `autoplan`. The build helper’s generated var-file filename also differs from the workflow’s input path. The unmodified demo therefore tests discovery of an unreferenced workflow, with zero explicit projects imported. A positive fixture must add an actual project, bind its workflow and supply the exact var file. Keep a separate built-in-step fixture for the first runnable import. [Demo config](../../../examples/demo-atlantis/atmos.yaml) · [Demo manifest](../../../examples/demo-atlantis/stacks/deploy/demo.yaml)

## Working with the saved stack

Suppose the selected Atlantis project `network-dev` declares `dir: infra/network`, uses Terraform workspace `default`, and passes two literal var files to plan. If the user chooses Atmos stack `dev`, show all three names in the preview: Atlantis project `network-dev`, Atmos component `network` in `dev`, and Terraform workspace `default`. In a new repository, configure `components.terraform.base_path: infra` in `atmos.yaml` and preserve the existing backend as specified in the Terraform PRD. The proposed saved entry is:

```yaml
# stacks/dev.yaml
components:
  terraform:
    network:
      metadata:
        terraform_workspace: default
      vars:
        - !include ../infra/network/vars/common.tfvars
        - !include ../infra/network/vars/dev.tfvars
```

This example uses the [proposed ordered Terraform vars syntax](terraform.md). Run `atmos stack instances -s dev` and `atmos terraform plan network -s dev` from the saved project. Retain the source Atlantis project identity in the import mapping so a retry can distinguish projects even when directory and workspace coincide. Preview the location of any provenance metadata that will be persisted.

Importing `network-prod` into prod creates or extends `stacks/prod.yaml` using that project's own workflow evidence. Adding another project to dev extends its existing manifest. If the chosen project resolves to a Terragrunt unit, save the [Terragrunt unit import](terragrunt.md) and any representable project-specific configuration. An unresolved workflow remains visible in the inventory-only preview and must never produce a runnable placeholder. Verify the imported addresses from a fresh checkout with the original Atlantis pipeline still in place.

## Specification audit and mapping decisions

Baseline: Atlantis **v0.50.0**, repo-config **version 3**. Upstream also accepts version 2. Treat v2 as a separate compatibility fixture before enabling it. The tables describe proposed inbound translation. Existing Atmos primitives are linked as implementation anchors. A mapping is verified only when a fixture reproduces the source behavior. [Pinned repo schema](https://github.com/runatlantis/atlantis/blob/v0.50.0/server/core/config/raw/repo_cfg.go) · [Project schema](https://github.com/runatlantis/atlantis/blob/v0.50.0/server/core/config/raw/project.go)

**Direct** means an existing primitive represents the input. **Conditional** requires additional evidence, a scoped translation or the proposed adoption syntax. **CI-owned** means retain the behavior in Atlantis or the VCS and surface it in the import report. CI-owned settings that affect credentials, inputs or plan production can still block local-plan readiness.

### Repository and project fields

| Source field(s) | Disposition | Atmos destination and boundary |
| --- | --- | --- |
| `version`, `projects`, `workflows` | Conditional | Validate the source version, expand YAML anchors and merges, enumerate projects, resolve workflow references. Preserve field paths and distinguish absent values from explicit false. Flag unknown keys. |
| `projects[].dir`, `name` | Conditional | Map the repo-relative project directory to the existing component source path. Use the project name for selection and provenance. Propose the Atmos component/stack pair and detect duplicate addresses before writing. |
| `workspace` | Direct for a resolved Terraform CLI workspace | Set `metadata.terraform_workspace`, including the effective default. Check backend settings separately. |
| `terraform_distribution`, `terraform_version` | Direct for explicit supported binaries and versions | Select the Terraform/OpenTofu executable through component `command`; pin the corresponding tool through `dependencies.tools`. A Terragrunt wrapper may supply a different actual executable; inspect the workflow. |
| `workflow` | Conditional | Resolve the named repo or server workflow and analyze each stage below. Apply Atlantis defaults only with evidence for the effective workflow. |
| `autodiscover.mode`, `autodiscover.ignore_paths` | Conditional | Scope directory discovery and apply explicit-project precedence. Test ignored directories and mixed explicit/inferred inventory. |
| `autoplan.enabled`, `autoplan.when_modified` | Conditional | Automatic PR execution stays in CI. Literal paths can inform `dependencies.files` and `dependencies.folders` for affected detection. Translate glob rules only after testing project-relative rebasing, negations and the complete changed-file selection. A watched tfvars file is never sufficient evidence of a plan input. |
| `depends_on` | Conditional | Resolve project names to unique Atmos addresses and consider `dependencies.components`. Check ordering **and** affected propagation: an Atlantis PR apply constraint alone does not authorize widening every Atmos run. |
| `execution_order_group`, `parallel_plan`, `parallel_apply`, `abort_on_execution_order_fail` | CI-owned | Compare with stack lifecycle DAG execution for a future CI migration. Group barriers, parallelism and failure propagation need separate equivalence tests. Never manufacture permanent component dependencies solely from group numbers. |
| `branch`, `allowed_regexp_prefixes` | CI-owned | Preserve the branch restriction and permitted project selectors in the report. Obtain the base branch when needed to resolve the project. |
| `plan_requirements`, `apply_requirements`, `import_requirements` | CI-owned | Carry forward each effective VCS gate and its stage. Atlantis `import_requirements` governs Terraform resource import; reading this configuration creates no resource-import permission. |
| Repo/project `repo_locks.mode`; project `repo_locking` | CI-owned | Resolve the effective repo lock, including its legacy spelling. Terraform backend locking and `flags.lock` protect a different resource and cannot implement this gate. |
| `automerge`, repo/project `delete_source_branch_on_merge` | CI-owned | Preserve VCS merge/cleanup behavior and overrides. No stack-manifest write. |
| `emoji_reaction`, repo/project `silence_pr_comments` | CI-owned | Retain as PR presentation settings. |
| Project `policy_check`, `custom_policy_check`; repo `policies` | Conditional evaluation, CI-owned approval | Match evaluator, policy inputs and enforcement point before proposing Atmos policy validation. Inventory Conftest version, policy sets and approval behavior separately (below). |

### Workflow stages and step vocabulary

Each workflow can specify `plan`, `apply`, `policy_check`, `import` and `state_rm` stages with ordered `steps`. Record readiness per stage. The same step can have different behavior depending on the preceding steps and the server environment. [Stage declarations](https://github.com/runatlantis/atlantis/blob/v0.50.0/server/core/config/raw/workflow.go) · [Step decoder](https://github.com/runatlantis/atlantis/blob/v0.50.0/server/core/config/raw/step.go)

| Step | Candidate Atmos primitive | Evidence needed to mark the stage reproducible |
| --- | --- | --- |
| `init`, `plan` with optional `extra_args` | Terraform init and plan, typed flags, variables, backend settings | Preserve argv order, CWD, selected workspace and the scope of each option. Resolve generated files, tool versions and credentials. |
| `show`, `apply` | Terraform show and apply with a saved plan | Track the actual producer of `$PLANFILE`, the plan presented for review and any JSON output consumed by policy. Apply the reviewed artifact under the original gates. |
| `policy_check` | Atmos policy evaluation where inputs and evaluator match | Reproduce the policy result over the same plan JSON. Approval owners and bypass conditions require CI handling. |
| `import`, `state_rm` | Terraform import and state rm | Report explicitly as state-changing stages and preserve their arguments and gates. Adoption never invokes them. |
| `env` | Component `env` for stable component-wide values; step-scoped environment otherwise | Preserve `name`, literal `value` versus derived `command`, shell, lifetime and secret references. Avoid expanding a later step's environment into earlier operations. |
| `multienv` | Workflow preparation with explicit environment outputs | Resolve all exported names and downstream consumers. Unknown command output makes dependent stages unresolved. |
| `run` (string or object) | Recognized native operation, scoped hook or ordered workflow step | Match command, working directory, environment, shell and `shellArgs`, exit behavior, and artifact production. A repository script requires inspection. Preserve `output` behavior, including hidden output and regex filtering, before reproducing its logging. |

### Policy and server context

The repo policy block can declare `conftest_version`, `owners.users/teams`, `approve_count`, `sticky_policy_approvals`, `policy_item_regex` and `policy_sets`. Each set has `name`, `source`, `path` and can specify owners, approval count, sticky approvals, item regex and `prevent_self_approve`. Map local or GitHub policy sources to an equivalent evaluator only after verifying policy resolution and input format. Keep approval counting, identity, self-approval and persistence of approvals in CI until separately implemented. [Pinned policy schema](https://github.com/runatlantis/atlantis/blob/v0.50.0/server/core/config/raw/policies.go)

The server's matching repo rules can determine defaults, permitted overrides, custom workflow availability and pre/post workflow hooks. Accept supplied effective server context as separate evidence. If a pre-workflow hook generates projects or a server workflow prepares the backend, mark the corresponding inventory or stage incomplete until its inputs are available. Never execute scripts while auditing the file. Record source, effective value, destination, disposition and unresolved reason per field in the preview. [Server-side rules](https://www.runatlantis.io/docs/server-side-repo-config.html)

## Custom workflows

Analyze ordered steps per stage, including relevant init, pre-plan, plan, policy and apply behavior. Track the files, credentials and environment inputs consumed or produced by a step. Resolve known values such as a declared project name or workspace. Preserve shell argument boundaries and the order of literal `-var-file` and `-backend-config` arguments. Inspect imported configuration without executing its shell during discovery.

1. **Fully understood plan.** A built-in init and plan with resolvable inputs can become a runnable local plan. A recognized shell sequence qualifies only when the importer understands its prerequisites and outputs.
2. **Unresolved preparation.** If a script generates the backend or assumes a role, identify the project, stage, script and missing behavior. If a known required file is missing, offer a file selection. A file selection alone cannot establish equivalence for an unknown script. Offer inventory-only import or skip. An inventory-only record must stay out of executable bulk selections.
3. **Independent apply behavior.** An understood local plan can coexist with a custom Atlantis apply. Leave that stage in Atlantis. When claiming apply compatibility, verify that the exact reviewed plan artifact reaches apply and that required gates still run. List stages with separate readiness and reasons. [Atlantis custom workflows](https://www.runatlantis.io/docs/custom-workflows.html)

For literal Terraform workflow flags, reuse the [existing declarative defaults](terraform.md#execution-flags) when their command scope matches. For example, a plan-only `-refresh=false` must not become a component-wide default that also changes direct apply. Surface a scope mismatch during preview.

## Acceptance

- Run both demo-derived fixtures above. In the bound shell-workflow case, identify the workspace, referenced file and reviewed plan artifact as evidence for manual follow-up. Keep the stage unresolved until a later translator proves each ordered step and its prerequisites. Removing the referenced file must identify the missing input.
- Check matrix coverage against the pinned repo, project, policy and step schemas. Fixtures must exercise server overrides, a negated watch glob, policy approval, stage-scoped env, and a state-changing stage that preview leaves unexecuted. Unknown keys remain visible.
- Two projects share a directory but use different workflows. Each preserves its own workspace, inputs and backend arguments. A repeated import is idempotent.
- A missing server workflow blocks only the affected stage/project. In a terminal offer actionable choices. With prompting disabled, identify the project, missing input and available selectors.
- An unknown pre-plan hook or shell substitution is never executed by preview. A custom apply alone does not block an independently reproducible local plan. No import modifies the team's existing Atlantis pipeline.
