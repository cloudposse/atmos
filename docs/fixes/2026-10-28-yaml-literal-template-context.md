# Fix: Restrict native YAML tag shielding to YAML template sources

**Date:** 2026-10-28

## Summary

Decoded step commands, names, and import paths now render their template expressions even when ordinary text contains `!literal`.

## Context

The generic template renderer applied YAML source scanners to every input. For example, `echo !literal "{{ .vars.stage }}"` retained the expression instead of producing `echo !literal "dev"`. Prefixed custom-delimiter arguments and decoded names and import paths had the same problem. These failures reproduced twice. The unquoted `echo !literal {{ .vars.stage }}` already rendered correctly and remains a passing control.

## Changes

- Mark raw stack manifests and serialized YAML sections explicitly as YAML template source. Keep datasource rendering in YAML document mode.
- Run native-tag source shielding only in that mode. The Starlark source protector also recognizes native literal tags, so it uses the same boundary.
- Keep encoded literal shielding in every context, including custom delimiters and repeated passes. Ordinary expressions referencing literal data retain normal evaluation behavior.
- Add regressions for decoded text, import paths, names, encoded literals, and native literal tags generated by raw manifest templates. Existing raw-template and stack-literal tests cover preservation through loading and evaluation.

## Validation

- Reproduced the quoted and prefixed failures twice before implementation; verified the exact unquoted control twice.
- Passed the focused template, stack-literal, source-protection, and import regressions twice with Go 1.26.10.
- Passed race-enabled template, literal, import, delimiter, and Starlark regressions with coverage.
- Passed `go build ./internal/exec`, fix-record validation, and `git diff --check`.
